# Implement Sim Platform

Start in the Sim checkout containing the requested product work. Read the [Platform contract](../../../apps/sim/platform/AGENTS.md) and [component ownership map](../../../apps/sim/platform/docs/component-ownership.md). These versioned files carry the current rules into a fresh chat. Use the [Platform README](../../../apps/sim/platform/README.md) for the local routes, fixture states, generators, and verification commands.

1. **Establish scope on the real route.** Identify the product entry, interaction, and affected consumers. When rebuilding an existing workflow, trace the old navigation target, its access gate, and the actions reachable by that viewer. Use that evidence to decide which controls belong on the new page before consulting the broader API or provider catalog. Foundations and the library live in the EMCN packages; working UI and transient interaction state live in the route, with examples supplied only by a fixture build (`SIM_PLATFORM_FIXTURES=1` at build time); real data and operations arrive through the data seam. Reuse the same renderer in the browser and Sim Desktop. Read the installed Next guides for the file structure or framework behavior you are changing.
   For organization Settings, work from the Settings rows of the [parity ledger](../../../apps/sim/platform/docs/org-parity.md): each row's Legacy source column names the old section, so inventory its viewer/deployment gates and every action reachable from it. Map old header buttons to the row or section they act on. Verify the same destination and drilldown on the fixture and authenticated routes; keep real writes outside fixture sessions.
2. **Resolve design intent.** For Paper-backed work, load the Paper MCP's guide (`get_guide`, topic `paper-mcp-instructions`), then use Paper to locate the live Shared or Platform master and the product states that use it, from the Shared, Platform and Product files only. Preserve the key and theme roles. Treat artboard sizes as reference measurements. For code-first changes, follow the latest explicit product direction and inspect the rendered route. Identify any source you could not verify. Update the Paper canvas when the request includes Paper changes.
3. **Choose the owner.** EMCN is frozen: compose it as it stands and pass it no new attribute, variant or option; only the design owner changes it (`check:emcn-surface`). Shared controls and foundations belong to `packages/emcn`; Platform-specific compositions belong to `packages/emcn-platform`. Auth and Docs compose the same Shared primitives through their own packages. Use public family subpaths, colocated CSS Modules and the single scoped style entry for each surface. Keep `@sim/emcn-legacy` outside the modern package graph. Start with the behavior. An action, navigation row, value picker, or disclosure has an existing keyboard and pointer contract. Different interactions may share visual roles while retaining different semantics. Use the existing family and named props for a change in size, intent, icon, or content. Toolbar choices use ChoiceMenu, as Home's period does; Select/SelectField belong to labeled forms and to a settings row's preference (`SettingsRow field`, as Paper draws Theme). Row roles and toolbar filters use compact text triggers without borders or chevrons. Fields carry no hint line; form dialogs, settings pages and settings rows carry Paper's one-line description. Compare the rendered trigger, not just its variant name. Put unique anatomy and its CSS together in `_components/<component>/<component>.tsx` and `<component>.module.css`. Match an existing semantic rhythm, such as Home's ActivityRow, for a custom composition. Keep page files free of styling. Only EMCN owns the appearance of its controls. Use Base UI there for complex keyboard, floating, and dismissal behavior.
4. **Trace the full change.** On a second independent feature use, move the original implementation to the nearest shared product owner (`app/(product)/_components/`) and migrate both callers. For consolidation, compare semantics, map every consumer to its replacement, then remove the obsolete implementation, export, variant styles, and unused registrations. For deletion, also check menus, preferences, fixture data and tests that existed only for the removed feature. Preserve unrelated consumers and historical Paper evidence. A feature composes the existing EMCN primitives in its own owner; a label, icon, data value or responsive arrangement is composition, never a variant. `CODE_FIRST_VARIANTS` and the catalog's Paper evidence govern only the variants EMCN already has; never an empty evidence list. Keep the public API small enough to understand at the call site. Edit the source or compiler for generated foundations and recipes. Before moving files across packages or renaming widely, merge the base branch and tell its owner, so parallel work lands before the move rather than against it.
5. **Verify where people use it.** Run the design audit and applicable checks from the README. Render the changed product route with empty, full, stress, and fixture-off data as relevant. Check both themes, widths between artboards, long content, text scaling, keyboard, and pointer states. Compare shared controls in their actual consumers. Check the actual scroll edge and the open popup when space is tight. For shell, panel, or desktop work, exercise the real Electron renderer. For substantial implementations and consolidations, use an independent agent during design or implementation and for a final review of the changed owners and routes. Preview fixtures with `SIM_PLATFORM_FIXTURES=1 bun run dev` in `apps/sim` (`/o/sim/home`) and live data with `bun run dev`. A separate worktree is a separate copy of the code; check which checkout serves a running preview before relying on it. Provide the working route for visual review.
6. **Keep non-UI code in one place.** Data, adapters and logic go in `apps/sim/platform/lib/data`, pure helpers in `apps/sim/platform/shared`; routes never hold a second copy. Build organization links with `surfaceHref` and the view's `useSurfaceScope()` (see "Product root and shell" in `apps/sim/platform/AGENTS.md`).
7. **Keep decisions durable.** Follow the contract’s maintenance guidance when an approved correction changes a shared rule. Record feature-specific decisions with their feature. For sustained work, keep a task checkpoint with the code revision, verified states, evidence, and outstanding work. Include the branch or PR, checkpoint path, and localhost route in a handoff. On resumption, compare the checkpoint with the current branch, working tree, and relevant live sources before acting.

## Review mode

When `cleanup` or a reviewer asks for a read-only review of Platform files, skip the steps above and:

1. Read the [Platform contract](../../../apps/sim/platform/AGENTS.md) and the per-job table in [`sim-platform-views.md`](../../../.claude/rules/sim-platform-views.md).
2. Check each changed file under `apps/sim/app/(product)/**` or `apps/sim/platform/**` against both: every job uses its one pattern, EMCN is composed as it stands, page files hold no styling, loading paints nothing, data and logic sit in `platform/lib/data` or `platform/shared`, and organization links go through `surfaceHref`.
3. Run `bun run check:platform-design` and `bun run check:boundaries`; each failure is a finding.
4. Return every finding as file, line, the rule it breaks (document and heading) and the exact before/after. Edit nothing.
