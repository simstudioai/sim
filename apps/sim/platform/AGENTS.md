# Platform design contract

Applies to this independent Next.js application, the zone served under the `org` base path. `embedded/` is not part of that application; it has [its own section](#embedded-in-the-organization-surface). “EMCN” means the modern shared system in `packages/emcn`, derived from this Platform implementation. `packages/emcn-platform` owns Platform-specific compositions. The old application uses `packages/emcn-legacy`; its chrome remains outside the modern package graph. For new work or design drift, run the repository's `$implement-platform` skill. Its Paper companion is `$sim-paper-design`. Never import the legacy app, styles, chrome, business logic or providers across this boundary. Real data crosses only through the [data seam](#phase-3-data-seam).

## Ownership

| Paper authority | Code owner | Consumer |
| --- | --- | --- |
| Shared: Styles, type, icons and media | `packages/emcn/src/styles`, `fonts`, registered geometry/assets | Auth, Docs and Platform recipes |
| Shared component masters | `packages/emcn/src/components/<family>/` | Other components and product compositions |
| Platform-specific compositions and Paper evidence | `packages/emcn-platform/src/components/<family>/` and `src/catalog/` | Platform routes and workbench |
| Product: Platform Core, Chat, Workspaces | A thin `app/(shell)/<segment>/page.tsx`; unique markup, interaction and a local CSS Module under `<segment>/_components/<component>/` | Route composition |
| Engineering workbench, outside Product | `preview/` | The separate /workbench route |
| Temporary example data | `fixtures/` | Server-only, default-off loader |
| Real data | `lib/data/` | The route composition that passes it to views |

Import modern families through their public subpaths, such as `@sim/emcn/button` and `@sim/emcn-platform/page-column`. Package-private `#emcn` and `#platform` aliases stay within their owner. The shared package never depends on a surface package, and no modern EMCN package may depend on legacy EMCN or application modules. App routing, fixture selection, authentication and data adapters stay in the app. Surface styles import shared foundations once; component CSS Modules stay beside their owner. Standalone preflight belongs to the app bootstrap, while the public Platform stylesheet is safe to embed.

Search existing EMCN and route owners first. For existing designs, follow Shared → Platform → Product and verify the stable Paper key, live Base and actual product Use (or a nested use rooted in one). Reference artwork, archive files, guides and specimen-only variants are not product uses. Do not use Marcus's files. Two systems that can share a recipe use Shared. If a second feature needs a page-owned component, promote the existing implementation, register it centrally and replace the original import in the same change. Do not copy it or import directly from another feature. Once product routes exist, remove unreached public variants from code and keep deferred states in Paper until a product or nested component needs them.

## Code-first product design

The running product and the latest approved direction govern implementation. Use Paper to identify anatomy, semantic roles and interaction states. A new shared visual variant requires at least two independent real consumers. Keep a one-feature composition local and compose existing primitives; do not add a variant for a label, icon, data value or responsive arrangement. Remove unused variants. Record Paper keys only if an actual counterpart exists. Preserve historical design evidence without constructing a fake counterpart. When an external interface is a visual reference, translate its proportions and behavior into Sim’s existing tokens and component names.

Keep routes thin. Colocate each feature component, its CSS Module and private helpers in `app/(shell)/<segment>/_components/<component>/`, with `<component>.tsx` as its entry. `(shell)/_components/` owns parts shared by its descendant routes (navigation, conversation composer, session). Generic controls live in `packages/emcn/src/components/<family>/`; import the same implementation everywhere. Each CSS Module belongs to its component folder. Use a barrel for a family with several public exports, not a redundant wrapper around every file. Base UI adapters inside EMCN may share the named `*.shared.module.css` button and popup recipes. Product components compose the corresponding EMCN controls through props. Custom feature anatomy still uses the same typography, row geometry and semantic rhythm as an existing comparable surface. The workbench may render product owners. Product code and its variant-use graph exclude workbench modules. No customer-facing development notices. Unimplemented external actions stay unavailable.

Use the shared semantic gaps from `@sim/emcn/styles/global.css` and Platform layout roles from `@sim/emcn-platform/styles/platform.css`. Title/detail stacks, sibling list items and adjacent actions each have a 2px role. The 8px row gap separates leading art from copy. Separate sibling rows with the list gap. Reserve lines for surface boundaries and data rules such as chart axes. Align a leading avatar or glyph with the first text line; center trailing metadata, badges and actions against the whole row. Align action ink with adjacent text by extending the hit area into the margin. Chat thinking, tool labels and prose share that text edge. Composer and message action groups use the same compact gap. Custom calendar, chart and summary rows use the same type and spacing. An icon that identifies a two-line notification aligns to the title; its trailing action group centers against the full row. Email thread counts and the notification trigger use the same centered inline label/count spacing. The notification trigger takes the compact secondary (Invite) button surface, and has no chevron. The tray applies control elevation once around its scroll viewport; stacked notices do not cast shadows on one another. An active popup stays above the tray, including at narrow widths. Labelled range pickers and inline ellipsis menus need accessible names, not redundant tooltips; keep tooltips on top-level icon actions.

Every Platform reading page uses `PageColumn` for the same centered, border-box column, with Home’s 1296px content maximum and fluid 16–48px gutters. `PageOverflow` extends surfaces 8px around the text edge. Home, Chat, Search, Settings, integration details, resource directories and people pages share these edges. Embedded editors and split preview canvases retain their available working space. PageColumn owns geometry only and preserves Home’s legacy theme isolation. Home and Integrations use the shared page-heading inset inside the moving content. The shell separately reserves clearance for its sidebar opener or native titlebar; responsive layout does not change either page’s own heading inset. The unpadded viewport keeps the fade at the window edge. The web sidebar opener belongs to the shell, outside the scrolling page. It stays at the expanded toolbar’s 12px top inset as the center content scrolls, including on Home and in the drawer layout. Keep the button reachable without covering page actions. Electron keeps both controls in its native titlebar. Keep the same shell inset immediately above and below the footer. Major dashboard/sidebar sections are independently spaced at 24px. Home uses the compact 3px heading gap from greeting to description, Recents to links and activity title to total. Use the 12px content gap from the Sim heading row to its input. Home widget content uses the 16px gap measured from the activity total to the chart, and from the attention, Email and Calendar labels to their first content. Header and calendar controls extend around their label line without adding height to these gaps. The ordinary 12px section gap still serves other compositions. Home has two inline alignment edges: headings and leading content share the reading-column text edge; the composer, row hover surfaces and outer control bounds extend by the shared 8px row inset. Keep Sim and the Build/Search toggle on the text edges, and align the composer with the leftmost recent and Email row on the left and the attention row and menu controls on the right. Measure the 24px dashboard gap between component boxes, including their inline hover overhang. Chart and widget boxes own that inset; the column layout allows for both insets so neighboring surfaces remain 24px apart. Vertical widget gaps use the same 24px as the description-to-Sim gap. Responsive layouts can wrap, collapse or split panels; button height, padding and type stay stable. Composer draft and placeholder keep the same type role across widths and themes; browser zoom and user text scaling still apply.

Use `ControlRow` for the sidebar, identity controls, panel tabs, recent links, wrapping workspace choices and horizontal destination links. The row owns its 30px height, 8px inset and the placement and hover of a 24px action, including a leading remove button that replaces an existing glyph. Workspace names, the Workspaces launcher and its tab title are text-only. A recent without a glyph keeps its remove action at the end. A pinned workspace or chat shows its pin in the row action slot. Hover or opening the menu reveals the ellipsis in place. On touch, tapping the resting pin opens the same menu. Sort pinned rows first, applying the section’s chosen order within each group. Keep the link, tab or button semantics on the rendered element, with sibling actions outside it. Whole section headers reveal their chevron on hover; identity controls need none. Ordinary buttons, icon triggers and rows share the sidebar Home radius (`--ui-control-radius`). Use `Button` / `IconButton` for actions and Base UI triggers, passing icons and labels through their slots; a toggle, such as a format on a selection, is a quiet Button with `selected`, never a hand-built button. A menu that opens where its surface measured a click (a canvas, a spreadsheet cell) is `PointActionMenu`. Buttons that open destructive confirmation dialogs use a quiet Button with `destructive`, including page actions, Settings rows, bulk actions and modal footer actions. It shares the menu row’s neutral resting paint and red hover recipe. Final confirmation actions retain the solid destructive variant. Close, clear and dismiss × controls keep their neutral hover; their glyph alone never makes an action destructive. The composer toolbar owns its round actions. Switches and segmented controls keep their pill shape. Clicking the selected half of a two-choice segment switches to the other half. Native keyboard choice navigation still selects its destination.

Use `Stack` for compact people or integration artwork: show at most three items, a passive `+N` overflow count, and each item’s name on hover. Counts remain intrinsic-width and use compact notation from one thousand; never replace them with an ellipsis action. Each hovered item shifts left by the shared inset without moving its siblings. Use the shared motion duration and respect reduced motion. `AvatarGroup` supplies people to the same stack for integration usage and calendar attendees.

Use `ActivityRow` for a first-line glyph, avatar or artwork stack, title/detail and centered trailing metadata. Its trailing metadata is either text or people, never both. A navigating row ends at its chevron and has no sibling action or ellipsis. Put record actions in its detail; a passive row with independent controls uses ActivityBody and has no whole-row hover or click target. Use the chart, calendar, composer or attachment owner when those parts have a different interaction. See the [component ownership map](docs/component-ownership.md) before adding another family.

Inputs and textareas share the neutral field frame, resting border and 8px text inset. Hover changes only the frame border; the fill remains unchanged. Focus alone preserves resting paint. Required placeholders describe the expected input without replacing the label. `viewOnly` supplies native read-only behavior and an always-visible shared copy action in the sidebar’s 24px trailing slot. Textareas place the same action at the top-right. Copy feedback remains visible for four seconds before returning to the copy action. Read-only fields show a not-allowed cursor without dimming, while their copy action remains interactive. TextArea defaultSize selects regular (76px), expanded (112px) or large (240px); skill instruction editors use large. Invite recipient fields share the regular textarea height and insets. Quiet `SearchField` is the explicit focus exception: its subtle underline starts at the typing edge, excluding the leading icon and trailing controls, and appears on hover or focus while the background remains unchanged. Counts inherit adjacent label metrics, use ordinary inline spacing and align on the text baseline. Disabled dropdown triggers and items retain their resting opacity, ink, border and fill with a not-allowed cursor; disabled behavior prevents activation, and hover/press never repaints them. Optional disabledReason descriptions use the shared tooltip and remain available to keyboard users. Supply them for non-obvious restrictions such as inherited access, protected administrators or unavailable prerequisites. Button and Checkbox expose the same optional reason; DataTable forwards selectionDisabledReason from its row metadata. Reuse the actual policy reason rather than a generic disabled message, and keep the control disabled while its explanation is focused. Secret reveal and copy use the same 24px icon action and field inset; text labels belong in their accessible names and tooltips.

Toolbar choices use `ChoiceMenu`, the same compact quiet button and menu as Home's activity period. A toolbar action uses the existing quiet compact Button or IconButton. Page-level actions live in the control bar beneath the title and description; an action for a particular record belongs with that record. `Select` and `SelectField` provide bordered field chrome only for labeled forms, including modal forms. Immediate preferences, row roles and toolbar filters use compact text triggers without borders or chevrons. Searchable, multiple-value and date-range pickers retain their specialized behavior with their text presentation composed from the same compact quiet Button; do not place a full-width field picker in a control bar. Reuse the existing owner for the interaction and compare its actual trigger with Home before accepting it.

Button-based field pickers use the owning Base UI Select.Label or Combobox.Label, through FieldFrame’s label slot, so clicking a caption focuses its control without closing and reopening the popup. A calendar popover uses a noninteractive caption explicitly associated with its trigger and displayed value. Text inputs retain native labels. Preserve selected values or counts in accessible names or descriptions alongside field hints and errors.

Measure the actual scroll viewport with `ScrollArea`, or attach `useScrollEdges` directly to a native or Base UI scroll owner. Use the shared 16px mask only on edges with more content, updating after scroll, resize, input, reset or filtering. Platform and Settings navigation hide the native scrollbar and keep their edge fades, keyboard, wheel and touch scrolling. Other scroll areas keep their existing scrollbar behavior. Insets establish resting layout; they cannot substitute for an edge fade. Home list widgets and notification panels use `--ui-widget-max-size` as a ceiling, not a forced height. The Home activity chart grows with its content and has no nested scroll viewport. Keep the dashboard free to scroll and let each overflowing list or schedule scroll independently beneath its stationary heading. Shared ScrollArea viewports and the Home calendar suppress rubber-band overscroll at their boundaries. Plain tooltips preview at most three lines; retain the complete accessible text. A structured people popover owns its content and uses the dropdown’s popup padding and row insets.

Form dialogs use `Modal` or `MultiStepModal`. Pass a title, content, action labels and handlers. A confirm handler that returns a promise holds the dialog open as pending, closes it on success, and keeps the draft with an inline message on failure; nothing dismisses it while pending. Returning `false` keeps it open at the dialog's next stage, and `onBack` turns the quiet footer action into a step back. The shared borderless surface positions its title at the logical start and supplies one quiet Cancel/Back. An optional footerStartAction accepts a standard button label, handler, intent and availability at the logical start; Cancel and confirmation remain at the end. Destructive editor actions require their own confirmation and never become the default focus target. Pending submission disables all footer actions. Command search and previews use the same shadow and dismissal layer. Form controls cannot construct or style a form header, footer or Cancel button. Opening a dialog or advancing its step focuses the first available field. Confirmation dialogs focus Cancel, and read-only previews focus Close. A nested dialog handles Escape one layer at a time. While a form is open, the global search shortcut leaves its draft and keyboard focus in place. Closing returns focus to the invoking control. Textareas scroll or grow within their owner and never show a manual resize handle. Modal and panel content uses the shared field family: TextField, TextAreaField, SelectField, SwitchField (a setting that applies with its switch, captioned on the leading edge), SecretField, RecipientField, FileField, DetailsField and ListField. Product dialogs provide values, labels and callbacks; they do not recreate field chrome. Full-width FileField centers its prompt without an upload glyph; its image kind supplies a compact preview and independent removal. DetailsField labels read-only information, and ListField owns grouped bullets and bounded scrolling. Use DataTable inside a dialog only for actual tabular data or selection, not static skill instructions. Recipient fields use the textarea’s height, draft typography and inset. Committed addresses use compact caption text and an always-visible neutral ×, like a panel tab. The remove button sits inside the tag beside its label; long addresses yield space to the button. Comma or Enter commits a draft, pasting a list commits its addresses, and Backspace from an empty draft removes the last tag.

ContentTabs uses Base UI tab behavior with the same ControlRow lane, spacing and paint as DestinationTabs. Its optional actions sit beside the tab navigation, outside its scroll viewport and arrow-key semantics. DataTable composes those tabs, native table semantics and shared checkboxes for controlled row/select-all operations. Its persistent toolbar places search at the start, filters at the end and sorting farthest right. A reserved selection count and caller-provided selection actions appear before the trailing filters and sort only when rows are selected. At zero selection the group is invisible, inert and excluded from accessibility, while preserving its layout space so neither sorting nor the table moves. Visible actions become disabled when inapplicable. There is no default Clear selection or mutation action. Passive table rows have no whole-row hover or click target; their controls remain independent. Consumers own filtering, sorting and mutation policy. Ordinary table values use regular-weight control text and normal ink; email and supporting values use secondary ink, not a heavier font. People tables use separate name and email columns where space permits, regrouping the identity on compact layouts and placing role controls beneath it at enlarged-text widths. Keep inline avatars, checkboxes and controls centered, and select-all visible in every layout. Column positions remain stable when filtering to zero rows, restoring results or changing selection. Use fluid column allocation and natural text wrapping when space is tight; do not force horizontal scrolling with minimum column widths. Preserve the action column when the table is empty. The table fits its reading column with the shared 8px surface overhang. PropertyList uses the same inline person mark and normal value ink, with intrinsic label tracks and a stacked layout only when space requires it.

MessageBubble owns the normal user-message surface and selectable integration ideas. Idea messages sit centered over full-width monochrome meeting artwork, with a translucent fill and at most two visible lines. Hover and press change the muted fill without adding a border. Selecting one appends the full prompt to the Home draft without submitting or discarding existing text or attachments.

Use `useClipboard` / `CopyButton` for successful copy feedback and `useFeedbackExpiry` for temporary status. Copied indicators and transient notices dwell for four seconds; repeated events restart the timer. Pause an actionable notice during hover or focus and keep its action available in the stack afterward. Icon color changes use `--ui-motion-color` (120ms, zero under reduced motion). Do not put literal timers or CSS durations in product components.

Opening a side-by-side panel keeps the chat title at the same inline and block position. A full-width panel takes over the reading surface until the reader returns to chat. Run disclosure controls thinking and tool activity. Assistant prose stays visible when activity collapses. Each chat message owns a continuous hover area from its content through its action row. Its timestamp and actions stay available when navigating by keyboard and on touch. Chat thinking, tool summaries and prose paragraphs share one 12px block gap. Expanded payloads have equal block padding; the final message keeps a section of clearance from the composer. Render pasted text, files and images with ControlRow and a sibling remove action. Tool summaries use one body-size label with quieter ink. A run divider, expanded tool rail and split-panel edge are structural rules with one shared hairline role. Ordinary list items remain separated by gap alone. Panel tabs, action controls and key values have their own semantics; the same CopyButton copies message text and either tool payload. Composer and jump-to-latest share their border, background and shadow; leave space between them.

Interface strokes have one non-scaling optical weight in CSS pixels. Size glyphs relative to the control’s type, capped at the shared icon size. Paint interface strokes with opaque semantic ink so overlapping segments do not darken; branded artwork and chart marks retain their own geometry. Neutral quiet controls gain the hover surface without changing ink. Destructive and primary confirmations change perceived lightness by the same amount within each theme; check rendered colors, not blend percentages. Destructive menu commands turn red on hover or keyboard highlight. A compact × dismisses a tab, recent, draft attachment or recipient with the ordinary quiet IconButton. Callers choose intent, never paint. A selectable menu row gains the same surface and promotes its glyph from secondary to primary ink on hover or active keyboard navigation. Selection, disabled and inverse controls have distinct semantics. Never change stroke thickness, spacing or radius on hover. Render interface glyphs through `Icon`. A unique data graphic may own accessible, labeled SVG and paint its own marks. Pointer focus alone adds no paint, except the explicitly requested SearchField underline.

Use [the shared Platform time formatters](shared/time.ts) for displayed ages, clocks, calendar ranges and chart dates. Keep raw instants or ISO calendar days in data. Relative ages use a single reference instant for the surface: now below one minute, whole minutes below an hour, hours below 24 hours, then `1d ago` until 48 hours. After that show an ordinal date, including the year when it differs. Preserve calendar days across time zones. Pass the viewer’s zone for a locally composed message. Fixture time is server-gated and fixed for reproducible rendering. A Home activity chart keeps one visibility setting and one period across modes: Build shows Tasks run and Search shows Searches. Both draw real dated daily counts; the axis, tooltip and Customize Home label must agree with the selected metric.

## Public API

- A page supplies data, semantic slots, supported variants and callbacks. It owns no CSS, inline styles, Tailwind classes or visual overrides, including layout around a component. A composition with its own spacing is itself a recipe with an owner. Keep the smallest readable recipe that serves the real callers. Layout belongs to the composition. Changes to a child control’s appearance belong to that control’s owner, including when a parent selector could reach it. No `className`, `style`, utility pass-through, arbitrary JSX prop spread or per-screen colors/geometry.
- Repeated data takes a typed array with stable item IDs. A specimen's row count is an example; render zero, two or more than the reference count without numbered props. Preserve genuinely distinct fixed slots.
- Keep the smallest API that describes the behavior. Prefer data, semantic slots and callbacks over combinations of visual flags. Do not add nested variant objects or independently tunable spacing, radius and color props. Use semantic HTML and import unstyled Base UI primitives inside EMCN for complex behavior. EMCN owns appearance. Base UI can own keyboard navigation, typeahead, focus management, dismissal and floating placement. Use named native controls for interactive masters and typed record arrays for repeated data. A static structural recipe does not provide those behaviors. A different label, icon, item count or viewport width does not create another variant.
- Pointer focus changes where typing, Tab and arrow keys go and adds no ring, outline, border change, shadow or background treatment, except SearchField’s shared hover/focus underline. Keyboard focus is visible: `:focus-visible` may paint, as review on the running app settled. Keep the caret, validation, hover, selection, open state and the active row during list navigation distinct. Exercise Tab, Escape, focus restoration and typing in both themes.
- Every value picker, including workbench fields and modal fields, uses the shared dropdown surfaces and row recipes. Use Select for choices, Combobox for search, and Menu for commands. Use Base UI's portalled positioner for root and nested popups, inside the active theme and modal layer. Submenus open on hover and by keyboard, preserve pointer travel into the child, and flip or shift within the available space. The parent and child close one level at a time with Escape.
- Keep tokens and composite recipes central. The Tailwind theme maps to semantic variables. An owner module may apply structural Tailwind utilities and registered theme roles; callers only use its public API. `PlatformSurface` selects the theme for the tree. Modules in an owner can express grid/flex, intrinsic sizing, focus, wrapping and overflow. Do not bake a screenshot into a component. At the default root size, match the Paper measurements retained by the current product direction. Use scalable type and spacing, bounded widths, flexible tracks, logical insets and natural height. Breakpoints follow a change in composition, not the number of Paper examples. Fixed stroke widths, icon geometry, touch targets and aligned data lanes are deliberate. Test intermediate widths, long content and zoom.
- Preserve theme roles, Geist and Geist Mono recipes, 16px directional overflow fades, shell/floating glass and quiet reading surfaces. Compare real semantic parts and nested controls, not just matching names. A gallery or a token declaration is not evidence that a variant is needed. Remove unused variants, their styles and documentation. When an explicit product direction revises Paper, implement it in the owning component and verify it on the real route.
- Default to Server Components. Keep browser event handling, focus, measurement and transient UI state at the leaf. Phase 1 supplies foundations; Phase 2 composes product routes and their unique parts; Phase 3 connects existing operations and real resources. No DB, API, global user state, auth or new schema in the design phases.
- The isolated project root owns its bootstrap and PostCSS entry; EMCN owns shared fonts and scoped surface styles. Keep the legacy root layout, proxy, globals and routes intact. Do not add a new provider or styling package just to define a variant.
- Only the server loader may import example data, and only when `SIM_PLATFORM_FIXTURES=1`. No fallbacks in components. Delete the fixture module/gate and workbench consumers together once real data takes over. Never write examples to storage, send an invite or imply successful backend work.

## Phase 3 data seam

Modern EMCN packages are the shared UI dependency. Only `lib/data/**` and `shared/` may import other application modules outside this project: query hooks under `@/hooks/queries/<domain>`, contracts and clients under `@/lib/api/<module>`, and the named helpers listed in `scripts/check-platform-design.ts`. `@/app/<route>`, `@/components/<name>` and the legacy `@sim/emcn-legacy` barrel stay banned there too, apart from named modules on that list, such as the chat hook. Add a helper to that list only after reading its runtime import closure.

The chat hook runs here unchanged. Views read a `ChatRuntime` (`(shell)/_components/chat/model.ts`), filled by `lib/data/chat.ts` on live data and by the session on fixtures. What the hook reaches that the zone answers more cheaply, `canvasShims` in `next.config.ts` replaces with a named module under `lib/data/shims/` saying what it drops. The workflow stores are real: the Workflows tab's canvas hydrates them in the same bundle. The shared socket provider, the chat hook and the modules around them also name workflow state, and one of them is on every page, so `workflowStateBridges` substitutes a bridge under `lib/data/shims/workflow-state/` for those importers alone: it reads an idle workflow until the Workflows tab connects the real stores, then follows them. That keeps the block, tool and trigger registry on the pages that need it. `check:platform-design` walks the seam's runtime closure and fails on any legacy view it bundles; the workflow seam folders and the canvas follow the scoped exceptions it documents (`workflowSeam`, `WORKFLOW_CANVAS_RULES`), and every other seam's walk stops at the workflow state the canvas owns.

Each `lib/data/<domain>.ts` wraps the existing hook and maps its contract shape to a Platform view model with a pure adapter. A domain whose views take the contract shape as it is has nothing to adapt: its `lib/data/<domain>/index.ts` is a barrel naming what crosses, with any hook of its own in a sibling file. A non-barrel module never re-exports. Never fork a hook, key factory, invalidation or contract; a hook that lacks a needed option gains it additively. A module's first import of a query hook that toasts resolves through `lib/data/emcn-shim.ts`, which webpack substitutes for `@sim/emcn-legacy` and which exports only `toast`, the `shared/toast.ts` sink the notification tray connects to. Any other name from that package fails the build, which is what proves no legacy UI entered.

Views that fixtures also render stay prop-driven. A route composes `data` and a named `actions` interface, filled by session state on fixtures and by mutations on live data. A surface that exists only on live data, such as a Settings section, People or Search, reads its domain's hooks from `lib/data` directly. No fixture branch inside a view. Hide what has no backend and record it in the [parity ledger](docs/org-parity.md); never fake it. Distinguish loading, empty and failure. A list reads `status` rather than treating empty as loading.

Loading paints nothing. Static chrome (headings, labels, menus, the composer, a calendar's hour grid) renders at once; data-backed content appears when its read settles. No skeletons, shimmer, placeholder blocks or loading copy anywhere in the Platform; a pending Settings section shows only its heading, and only when its loaded content carries that heading. Mutation labels such as "Saving…" are feedback on an action, not loading copy. No route has a `loading.tsx`: the shell's unkeyed `<Suspense fallback={null}>` around the page keeps the current page on screen through a client navigation, and on a page load paints the sidebar before the page. A lazily loaded part sits in its own `<Suspense fallback={null}>` inside the page's chrome, as People's chart does, so it can never suspend up to the shell and blank the page. One component decides which view a URL shows, and that same component renders the view's heading and Back link from the same `nuqs` state. A second reader, such as Next's `useSearchParams`, settles a few frames later and flashes the previous view's chrome.

A server read runs the same application use case as the route behind its contract, in process, with the viewer's session principal (`lib/data/server-read.ts`), and reads the result through `asRouteResponse`, so a result that drifts from the route contract fails as it would on the wire. Where the route has no use case, call the server helper it calls; never query the database from the seam. Only a `server-only` module may name a use case (`serverSeamHelpers` in `scripts/check-platform-design.ts`). A first-paint read lives in `lib/data/prefetch-<domain>.ts` under the hook's own key and `staleTime`, inside `withinPrefetchBudget`; it may never block or fail the page, so the client fetches what it gave up. `resolvePlatformMode` decides each server entry once: `fixture` with `SIM_PLATFORM_FIXTURES=1`, `live` with `DATABASE_URL`, otherwise `none`, today's empty rendering. Load the seam with a dynamic import behind the `live` check, so fixture servers never evaluate it. `readOrganizationSurface` reads the viewer's surface once per request, in the organization it is given, or in the one they joined first.

The legacy organization layout redirects flagged organizations here through `lib/platform/routes.ts`. Link out to a legacy route only with `legacyRoutes`, which builds an absolute URL, and only to a route that mapper leaves unmapped. Linking to a mapped route makes the two surfaces redirect to each other.

Organization Settings follows the organization surface’s groups, labels, order and viewer gates. Keep General’s secondary views behind its own rows. Place setup, create, manage and destructive actions beside the setting they affect or at the end of that section; the page heading identifies the page. Platform-only tools retain their own entry points without displacing the organization’s tabs.

Gates live on the server and arrive as data. Hiding an entry is navigation, not authorization: the API behind every page enforces the same rule. A Settings section plugs in by filling its folder under `settings/_components/sections/`, which `section-registry.ts` loads lazily; its navigation entry and gate are in `lib/data/settings-navigation.ts`.

## Embedded in the organization surface

`embedded/` holds the organization views and their data (`embedded/app`, `embedded/lib`). It is not a Next app and has no pages: the main app's `app/o/[organizationId]/` routes mount it, for every organization, whatever the `platform-org-ui` flag says. An edit here ships in the main app's build. It is built on the host, not on this project: it imports the host's hooks, stores, providers and packages, legacy chrome included (`WorkspaceChrome`, the legacy composer, Search's source cards), and the data seam and seam closure do not apply to it. `check:boundaries` sets its own seam: views read data through `embedded/lib/data`, and that layer points away from views and routes.

The zone and `embedded/` share only the modern EMCN packages (`packages/emcn`, `packages/emcn-platform`) and `shared/`. `shared/` holds pure helpers, view models and data adapters that take what differs as an argument. It imports neither tree, and from the EMCN packages only types. Neither tree imports the other, not even for a type (`check:platform-design` rule `zone-embedded`, `check:boundaries` rule 7), so a change to a view here does not change the zone, and a similar view in each is two views. `app/o` is the only legacy code that may import `@/platform/*`, and only `embedded/` and `shared/`; `check:platform-css` holds every other entry out, and `check:platform-design` holds `app/o` out of the zone.

Org context comes from a different place in each. A view here calls `useOrganization()` from `@/lib/organizations/provider`, which the `app/o` layout fills from `getOrganizationSurfaceContext`. The zone calls its own from `@/platform/lib/data/organization`. `surfaceHref`, `legacyRoutes` and `routePrefix` are the zone's and do not exist here: a link here is a host route (`@/lib/navigation/paths`). Each tree has its own `usePlatformNotices`. Both raise toasts through `shared/toast.ts`: the zone's tray connects to it with `connectToastSink`, and on `/o` so does `app/o/[organizationId]/components/toast-sink.tsx`, which sends them to the host toaster as its module loads. `PlatformSurface` collapses inside another, so a part can wrap itself when it alternates with legacy chrome.

The design rules in this contract hold here too. `check:platform-design` walks `embedded/`, excepting its imports of the host and the host tokens it names, and counts what predates that per file and rule in the shrink-only `scripts/check-platform-design.baseline.json`.

### Converging a domain

Markup differs between the trees; nothing else should. `check:platform-convergence` holds the line: the file count of `embedded/` only falls, and a new path held by both trees fails. To converge a domain:

1. Diff the pair. Compare each function, not just the file: a similarity score hides a reordered branch.
2. Move what is identical to `shared/<domain>.ts` and repoint importers, in both trees. No re-export is left behind.
3. Inject what differs: an argument (`useAccountDeletion`'s landing URL and cleanup), a hook passed in (`usePeoplePicker`'s `useSettledTerm`), or a factory (`createPreferences`, `createRowLinks`) when several hooks share the difference. The tree keeps a thin module that fills it in.
4. Check every field the merge adds against the other tree's views. A field one tree never set can change what the other renders, as `emptyMessage` would have on a zone picker that falls back when it is absent.
5. When the trees disagree on what a viewer sees, leave that one function in each tree and raise it. Choosing is a product decision, not a refactor.
6. Run `bun run scripts/check-platform-convergence.ts --update` and `bun run scripts/check-monorepo-boundaries.ts --update` to record the shrink.

## Workspace chrome

Opening a workspace never changes the sidebar. A workspace row, a command-search result or a workspace in the chat panel opens that workspace in the right pane, as the Integrations row opens Integrations, and the open workspace's row is current: Dashboard on example data, Workflows on live data. Every workspace page sits on one tab frame, listed with the data modes that serve it in `WORKSPACE_TABS`: Dashboard, Issues, Changelog and Logs from Paper, with one shared split for a record's details; Tables, Files, Knowledge bases and Workflows, live-only ports of the legacy pages with breadcrumbs as the only folder traversal; and Settings. The Workflows canvas is the one surface that keeps legacy pixels: the user required blocks, handles, edges, loops and parallels to look exactly as they do in the legacy editor. Its folder copies the legacy canvas views and is exempt from the styling rules it cannot meet; the chrome around it follows this contract. Workspaces and chats partition pinned items first, then apply the section’s chosen sort within both partitions. The pin occupies the row’s trailing action slot and gives way to the ellipsis on hover or when its menu opens. Use the Home review book glyph for documentation throughout the Platform. ## Product UI and desktop

- Keep a draft or interface edit in memory for the lifetime its user expects. A chat draft belongs to its chat; profile edits and inbox read marks belong to the product session. Navigating away and back must preserve them. A new fixture scenario starts a fresh session. Popups and cancelled edits stay local to the control.
- The same product entry under `app/(shell)/` serves the web browser and the existing `apps/desktop` Electron shell. Feature-detect `window.simDesktop` in the typed desktop adapter only. Consult the shared `@sim/desktop-bridge` contract and native titlebar observer. Electron owns real window controls and privileged operations. Reserve their inset only in a native window; keep interactive areas outside drag regions. Do not draw traffic lights, mock the bridge in product code, or fork pages by viewport or user agent.
- On every shell or panel change, test the real Electron window as well as web, keyboard, narrow and intermediate layouts. Exercise inset/fullscreen, sidebar expand/collapse, panel takeover, tabs and focus return. Browser-only views must remain usable without the preload. Native capability integration remains Phase 3.
- Keep data-specific layouts such as calendar time slots, chart marks and tool payloads in their feature owner. Promote a repeated interactive row to EMCN and migrate the original consumer; attachment previews, form controls, menus and data actions each retain their semantic owner.

## Maintaining preferences

Treat an explicit correction as a change at the narrowest owner that explains it. For a Platform-wide rule, update this contract and the shared implementation it describes. Update the [ownership map](docs/component-ownership.md) if responsibility moves. For a feature-specific decision, update that feature and its product reference. For a change in how agents work, update the [tracked skill](../../../.agents/skills/implement-platform/SKILL.md). Keep machine-local memory and editor instructions as pointers to the versioned rules.

When removing or consolidating a component, trace its real callers. Migrate their data, keyboard and pointer behavior before retiring the old exports, styles, variants and unused fixture or workbench references. Prefer a narrow audit for a rule that code can reliably detect, and a rendered regression for behavior that has failed in practice. Demonstrate the failure on the old implementation. Preserve dated design evidence separately from current product decisions.

## Shared local review

Keep one user-facing Platform preview at `http://localhost:3125`, served with `dev:platform` from the agreed review checkout. The preview follows that checkout’s files; commits on other branches or worktrees do not appear automatically. At session start, inspect the listener’s working directory, branch and uncommitted changes, then reuse it. Do not start a second review server or silently choose another port. Parallel tasks may use separate branches for review, but their changes must be reconciled into the shared preview checkout before handing the UI back. Preserve concurrent work and identify the preview owner in a checkpoint. Temporary automated-test servers are isolated from review and must be stopped afterward.
