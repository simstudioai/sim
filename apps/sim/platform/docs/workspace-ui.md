# Workspace UI

Open [a workspace](http://localhost:3000/workspace/it/dashboards?state=full) on a development server started with `SIM_PLATFORM_FIXTURES=1`, or a seeded workspace on a live one. A workspace row in the sidebar, a command-search result and a workspace in the chat panel all open the workspace: Dashboard on example data, Workflows on live data, as legacy opens a workspace. The organization sidebar stays as it is and marks the workspace's row current, as it marks Integrations; only the page on the right changes.

| Route under `/workspace/[workspaceId]` | UI owner |
| --- | --- |
| The workspace itself | Redirects to `dashboards` on example data and `workflows` on live data (`workspaceHome`). |
| `dashboards` | The workspace's read-only dashboard: example snapshots on fixtures, and the dashboard document Sim wrote on live data. |
| `issues`, `issues/[issueId]` | Agent-proposed issues in four groups, and an issue's proposal, impact and evidence with decisions in its control bar. |
| `changelog`, `changelog/[entryId]` | Applied changes (live: published releases) by day, and a change's details with the workspace items it touched. |
| `logs`, `logs/[runId]` | Runs with a period, filters and sort, or their dashboard, and a run's trace, selected step, payloads, files and cost, with Stop, Retry and its snapshot on live data. |
| `tables`, `tables/[tableId]` | Live only. The workspace's tables and folders, and a table's grid. |
| `files`, `files/[fileId]` | Live only. Files and folders, and a file's viewer and editor. |
| `knowledge`, `knowledge/[knowledgeBaseId]`, `knowledge/[knowledgeBaseId]/[documentId]` | Live only. Knowledge bases and folders, a base's documents and connectors, and a document's chunks. |
| `workflows`, `workflows/[workflowId]` | Live only. Workflows and folders, and the workflow editor. |
| `workflows/runs/[executionId]` | Live only. A run's frozen workflow, opened from the run; it lives here because only the Workflows tab loads the block registry. |
| `tests`, `tests/[name]` | Live only, behind the `workflow-tests` flag. The workspace's workflow tests with Run all, and a test's latest or chosen run in the Logs run-details anatomy. |
| `settings`, `settings/[section]`, `settings/secrets/[credentialId]` | Live only. The workspace's Settings: its sections beside their navigation. Example data keeps the tab empty. |
| `upgrade` | Redirects to the plan picker, `/settings/billing/plans`, keeping `reason`. |
| `home`, `chat/[chatId]`, `integrations`, `skills`, `access-requests` | Live only. Moved legacy URLs: each page authorizes the workspace, then redirects permanently to its organization's page through `lib/data/legacy-redirects.ts`, which maps the URL with `mapLegacyWorkspaceUrl` (`@/lib/navigation/legacy-redirects`) (the Settings route does the same for organization section keys). |
| `files/[fileId]/view`, `w/*`, `task/[chatId]` | Moved legacy URLs, redirected statically in `next.config.ts`. |

The bare `/workspace` opens the viewer's last active workspace, or a workflow `redirect_workflow` names, honoring `redirect=upgrade|settings`; a viewer with no workspace goes to the organization's landing, sees why one cannot be created, or gets a first workspace created (`lib/data/workspace-entry.ts`). A workspace page that fails or is missing renders the workspace's own `error.tsx` and `not-found.tsx`, which do not say whether an inaccessible workspace exists.

`WORKSPACE_TABS` (`lib/workspace-navigation.ts`) lists each tab with the data modes that serve it and, for Dashboard, Changelog and Tests, the runtime flag it needs on live data; the tab bar shows only the tabs the server's mode and the organization's flags serve (the layout passes the flags from `readWorkspaceTabFlags`). `hidden` keeps Dashboard, Issues, Changelog and Tests out of the live tab bar, and out of chat and mentions, until Emir's pass; on live data each still answers when its flag is on and is not found when it is off (Issues, with no backend, always). Dashboard, Issues, Changelog and Logs follow Paper; Tables, Files, Knowledge bases and Workflows are code-first ports of the legacy pages, exactly feature compatible apart from the removals below. A workspace has no chat or skills page here: chats belong to the organization, and the composer's slash offers skills. Skills are authored, per workspace as legacy scopes them, in Integrations › Skills (`/integrations?tab=skills&workspace=<id>`).

## Workspace pages

Dashboard, Issues, Changelog and Logs are one family of Platform pages, styled from Home and Integrations. [Dashboard](http://localhost:3000/workspace/it/dashboards?state=full), [Issues](http://localhost:3000/workspace/it/issues?state=full), [Changelog](http://localhost:3000/workspace/it/changelog?state=full) and [Logs](http://localhost:3000/workspace/it/logs?state=full) open on any fixture workspace; `?state=stress` exercises the extremes and `?state=empty` every empty state.

- **Frame.** `WorkspacePage` puts the workspace name and description in the Integrations heading, the workspace's tabs (`workspaceTabs`) in DestinationTabs and the tab's ControlBar beneath them, at the same positions as the integration center. Issues' search field fills the bar's leading edge; elsewhere the choices lead, each at its text width as Home's period is. Logs has no search: its status, trigger, workflow, folder and period choices lead (a custom period adds its range picker), and the Runs/Dashboard view, Export and sort end the bar. Like Home's controls, the bar's surfaces stay inside the column and their text is inset, so a leading choice lines up with the tab labels above it. The page is at least the viewport tall, so an empty state centers in the space below the controls.
- **Rows.** Lists follow Paper's rows and the shared recipes. Issue groups take Integrations' group title with a chevron; an issue row is a caption ID, a one-line title and a right-aligned date. Log rows put duration, Compute Units and start time on the right (RunRow). Changelog entries take ActivityRow's title, detail and meta roles in Paper's ChangeEntry order: title and time, the description, then the contributor with the ticket at the end of the row, under the time. The dashboard's typed table is EMCN DataTable.
- **Details.** `DetailSplit` is shared by issue, change and run details: Paper's ticket bar puts the Integrations Back chip and the record's actions on one row, and a record's identifiers (an issue's ID, a run's execution ID) are among its facts. A reading column scrolls with its edge fade beside a rail with a 24px inset; the rail's hairline boundary spans only its content, extending the same 8px above and below it. Issue and change details use a 280px facts rail. Run details keep the run's metadata fields and trace in the reading column and give the rail to the selected step: its facts, then input and output in Paper's trace-payload form with the chat tool payload's monospace. Metadata fields share columns from row to row and clamp each value to one line, with the full value on hover. The trace follows Paper's TraceRow: every row, the root included, has a disclosure slot, the step's mark and its name one 8px gap apart; each level indents by one disclosure, and a hairline guide (the conversation rule) hangs under each open parent's disclosure through its last descendant, as trace views in Braintrust and Vercel draw them. A payload renders one source line at a time, so a wrapped value keeps its indent with a further 16px hang, and shows its first 32 lines until the reader asks for all of them. Below a 45rem frame the record stacks and scrolls as one: facts above the reading column, an inspector below it. Record headings and section titles match Integrations' details (DirectoryHeading, T093). Decisions use the secondary compact Button, as Connect does.
- **URL state.** Issues' search, the filters, sort and period live in the URL through nuqs (`lib/workspace-views.ts`). A row carries its list's view into the record's URL, so the Back chip returns to the same filtered, sorted list.
- **Reading position.** A list remembers its scroll position when a click leaves it. Browser Back and Forward and the record's Back chip restore it; a tab or sidebar visit starts at the top. The router renders a history step inside the popstate dispatch and scrolls a link's destination into view itself, so the page restores on the next frame and marks the shell's scroller so the shell does not reset it.
- **Paging.** Lists reveal records in pages as the reader nears the end, with no label, spinner or end marker; the shell's edge fade shows content continues. A revealed count survives Back.
- **Refresh.** Pages refresh themselves; there is no refresh control. On fixtures Dashboard and Changelog say when their data last updated, new runs join Logs as they arrive, and example time holds the age and the list still. On live data the dashboard's range rolls forward every minute, the changelog says when it was read, and Logs reads its snapshot again once the server reports new or changed matching runs.
- **Session.** Example decisions on issues change only the browser session (`workspace-session/`). Nothing is sent or stored.
- **Data.** Each route is a server component. On fixtures it loads server-gated data and passes `data` to a client route, which supplies `actions` from the session. On live data it renders a live component (`live-dashboard`, `live-changelog`, `live-release`, `live-runs`, `live-run`) that reads the legacy hooks through `lib/data` and passes the same views their props; the frame names the workspace through `WorkspaceTabPage`. Issues has no backend, so its live URLs answer 404. See the [parity ledger](org-parity.md#workspace-pages).
- **Live Dashboard.** The dashboard is the one document Sim writes, not per-period snapshots, so live renders legacy's spec: its title and description, text, rows, tabs and stat, chart and table panels (the markdown embed's `components/dashboard-panel`), with legacy's range presets and custom calendar range, time zone, chart zoom and Reset in the URL. Behind the `dashboards` flag, as legacy is.
- **Live Changelog.** Releases have a version and a reason but no contributor or issue, so live entries show the version where the ticket goes. A release's details show its notes (read-only; Edit notes opens the file in Files), its change lines and the workflows it shipped, and an editor can change its title, version and reason. Behind the `changelog` flag; a permission group that hides Files closes it with legacy's Access required and access request (`access-required/access-boundary`).
- **Live Logs.** The server pages the list in the URL's period (legacy's ranges or a custom range), status, triggers, workflows, folders and sort; integration triggers are read from the trigger registry on the server. Export downloads the view as CSV (editors). A row's ellipsis and right-click carry legacy's menu: Retry, Stop, Copy run ID, Copy link, Open workflow, Open snapshot, Filter by workflow and Clear filters. The Dashboard view charts runs, errors and latency and lists each workflow's runs by segment. A run is addressed by its execution ID; its trace is rooted at the workflow with its input and output (hidden by `hideTraceSpans`), followed by its files and cost. Open workflow, View snapshot, Troubleshoot in Chat (failed runs), Stop (editors, while it runs) and Retry (failed runs) sit in the record's bar. The snapshot (`workflows/runs/[executionId]`) draws the run's frozen workflow with the executed blocks marked and opens a block's step in the inspector. Legacy `logs?executionId=` links open the run.

## Resource tabs

Tables, Files, Knowledge bases and Workflows share one frame. They run on live data only: each page calls `notFound()` unless `resolvePlatformMode()` is `live`, and the workspace layout mounts one shared realtime socket (`lib/data/realtime.tsx`, `WorkspaceRealtime`) for every tab, so no page opens its own.

- **Frame.** `LiveWorkspacePage` reads the workspace through `useLiveWorkspace` and renders the same heading, tabs and ControlBar as the Paper pages. The bar holds the tab's search and filters, with breadcrumbs in its `trail` slot to the right of search. A list fills the page (`layout='fill'`) and the workflow editor fills it without a reading column (`layout='canvas'`).
- **Breadcrumbs.** EMCN `Breadcrumbs` (`@sim/emcn/breadcrumbs`) is the only way through nested folders: the tab root, each ancestor folder and the current folder, separated by a chevron. Past four crumbs the middle collapses into a "…" menu of links, keeping the root and the last two. The current folder's crumb opens its commands; an ancestor crumb accepts a drop, so dragging rows onto it moves them up. The folder lives in the URL (`useFolderParam`), so Back returns to it.
- **Lists.** `ResourceTable` (`app/(product)/_components/workspace/resource-table/`) takes the Logs run list's anatomy: a caption header, 40px rows with a leading glyph or brand mark, secondary-ink supporting values and numbers on the trailing edge. Folders open in place and resources navigate. Rows carry their commands on an ellipsis and on right-click, join a checkbox selection with a bulk bar, rename in place, move by drag and drop and render only what is near the viewport. Pinned items sort first and show their pin in the row's action slot. Search, filters and sort live in the URL. "New" actions sit in the control bar and in search's "This page" group (`usePageCommands`).
- **Tables.** The list creates tables in the open folder. A table opens the legacy grid, ported whole into `tables/[tableId]/`: virtualized scrolling through every row, in-cell editing, selection, copy and paste, fill, row insert above and below, column insert, pin, resize, reorder, hide and delete, every column type from the registry, workflow and enrichment columns with their runs, filter, sort, find, Export CSV, the row modal, Table Security locks and live updates from other editors. Import CSV and table views are removed; hidden columns save with the table's layout.
- **Files.** The browser lists files and folders with new file, new folder, upload, unzip, download, drag to move, rename, share and delete. A file opens the legacy viewer and editors for every type legacy supports, including collaborative markdown, code, spreadsheets, PDFs, slides and images, with its per-file actions.
- **Knowledge bases.** The list creates, edits and deletes bases and their tags. A base lists its documents with upload, tags, enable and disable, retry and delete, and its connectors in a rail on the right, as Logs details keep their rail. Adding or opening a connector opens a modal in the Integrations credential style with every legacy operation: source and credential, configuration and selector fields, access, sync now, pause, edit and remove. A document lists its chunks in the Logs run list's anatomy, with search, enable and disable, edit and delete.
- **Workflows.** The list creates, imports, renames, locks, duplicates, exports, moves and deletes workflows and folders; a locked row shows its lock and cannot be dragged. A workflow opens the editor on the canvas layout: the header holds the workflow's breadcrumb (with rename, duplicate, export and delete), the more menu, Deploy and Run; the canvas is the legacy editor's, copied view for view, with the canvas controls at its corner and the Terminal docked beneath; the right panel holds the Toolbar (search, drag or click to add), the block Editor and Variables. Deploy's dialog has General (versions with rename, descriptions, compare, promote and load), API, Chat and MCP. Removed by product direction: the live workflow view and language examples in the deploy dialog, the editor's connections panel, canvas error notifications, the panel and floating chats and the floating variables window.
- **Tests.** A test list with search, sort and Run all; a test's details with the run picker, figures, staleness notices, cases and the workflows it ran against. Editing opens the test file in Files, and a ran-against row opens the workflow's current version.
- **Settings.** The legacy workspace settings sections, ported code-first on live data; example data keeps the tab empty. `settings/[[...section]]` renders the section through `settings/_components/workspace-settings-section/`, which loads only that section's folder in the browser, in the frame (`workspace-settings/`): the section navigation in the organization Settings navigation's pattern (`SettingsNavigation`, grouped chips with search) beside the section's title and body. `/settings` opens Teammates. `lib/data/workspace-settings` applies the legacy settings sidebar's gates from the workspace's host context, the viewer's permission group, requestable features, fork availability and the Sim Mailer entitlement: a section the viewer may not open is not found, one their permission group withholds but they may request shows Access required with Request access, and each section reads what it may change from `useWorkspaceSettingsSection`. Sections: Teammates, Secrets (with a secret's details at `secrets/[credentialId]`), BYOK, Sandboxes, Requests (the shared Requests panel with the workspace scope), Custom tools, MCP tools, MCP servers, Sim API keys, Sim Mailer, Recently deleted, Workspace forks and Custom blocks. Settings that belong to the viewer, the organization or the deployment (General, Desktop, Browser, Terminal, Subscription and Credit usage, Self hosting and the organization sections) are in organization Settings; see the [parity ledger](org-parity.md#settings-legacy-settings-homes).
