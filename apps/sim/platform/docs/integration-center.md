# Integration center

`/integrations` at the organization root is the member-facing management surface for Apps, Skills, MCPs and Credentials. Home and eligible organization workspace entry points navigate here rather than mounting another copy. A standalone workspace, or a viewer without the organization's Search access, retains the existing workspace credential route until an authorized replacement exists. Organization approval and source administration remain in Settings. Entering from a workspace must not silently turn a personal credential into an organization or workspace credential.

## Product structure

| Destination | Content |
| --- | --- |
| Apps | Connected apps first, then available apps filterable by category. Provider names and descriptions come from existing catalog metadata. Member credentials retain their provider detail routes. |
| Skills | Shared and Personal sections. A skill has a name, description and instructions, with ownership shown separately from its content. |
| MCPs | Shared and Personal sections for custom servers. Connection details belong to the server, not a fabricated provider catalog. |
| Credentials | Shared and Personal sections for named credentials and secrets. Show access in the list and ownership in the detail or editor, without exposing a secret in a list. |

Keep the heading, description, reading column and major gaps aligned with Home. DestinationTabs and the compact control bar follow the Platform Workspaces anatomy in Paper. Search sits at the start of the control bar; destination-specific sorting, filtering and create actions sit at the end. Category and access choices use ChoiceMenu, the exact Home period owner with a compact quiet trigger. Select/SelectField belong to the editor's form fields, not this toolbar. Tabs and the control bar use the same 12px section gap as Home’s wordmark and composer. Categories and ownership sections live in the content, not as another nested tab system. Empty results sit at the normal section-title edge immediately below the controls.

The route entry stays thin. `integrations/_components/integration-center/` owns the frame and destination composition. `resource-list/` and `resource-editor/` own the feature's list content and editor fields. Reuse EMCN DestinationTabs, SearchField, ActivityRow, Avatar, Button, Menu, Modal and Field owners. Base UI supplies complex behavior inside EMCN; product code supplies data and callbacks. Leading marks align with the first line, trailing people and actions center against the whole row, and lists use the same shared rhythm as Home email and notification rows. App rows end with two profile photos and a passive +N count before their navigation chevron. Individual photos reveal names on hover; the count opens nothing. Details use a natural-language usage line below the description. Skills use the slash glyph; credential keys share the central key geometry. Reconnection stays an account action, without an extra list status.

## Data and access

Apps retain the existing [member inventory and credential contract](organization-integrations.md). A connected account or an organization-approved provider does not prove that its credential is shared. Usage avatars and counts require an authorized roster projection; do not derive organization usage from the viewer's personal accounts or expose another member's credential label.

The full workspace app catalog is projected at generation time from existing public block metadata, suggested skills, templates and provider connection definitions. The fixture index receives compact summaries; the server sends operations, instructions, prompts and enrollment fields only for the selected detail. The metadata audit detects upstream drift. An app's generic `authType` is not a connection form: expose only methods present in the canonical provider definitions. Live inventory continues to come from its authorized operation.

## App and credential details

App-level actions belong in the control bar immediately beneath the title, description and usage line. Docs and Add credential use the same compact controls as the center. Actions that apply to one credential stay in that credential's row or detail. The app shows a Connected credentials section with multiple independently named records, then available suggested skills, templates and capabilities. Suggested skills can be inspected and added to the fixture library; template prompts can be inspected and copied. Bound long collections with the shared scroll owner and pagination.

Credentials retain their canonical ID across provider families. Editing a Google service account through Gmail updates the same record shown through Calendar and Drive. A credential detail exposes its name, description, connected identity, provider method, scope and effective access. Names and descriptions follow existing limits; secrets never enter lists or session metadata. Personal tokens have no sharing controls. Workspace credentials retain a named workspace and effective admin/member roles; organization-managed records retain their separate managed scope. Usage avatars are not permission evidence.

Admin controls follow the existing credential contract: edit description/name, reconnect, disconnect and share with eligible workspace members. Effective workspace-admin access cannot be removed or demoted here. Keep the last active explicit administrator protected. A member may leave an explicit share when those constraints permit. Preserve pending and revoked member states. UI examples demonstrate these distinctions; authorized application operations must enforce them when the data seam is implemented.

Connection methods preserve their actual requirements: OAuth scopes and provider environments, personal tokens, service-account fields, Google JSON, provider-specific client credentials and custom Slack bots. Choose a workspace explicitly when multiple eligible destinations exist; owner-only tokens remain personal. Reconnect preserves the credential ID and immutable provider host/environment. Transient secrets are cleared on close and before the metadata-only callback, with no storage or network mutation in fixture mode. A local metadata record does not imply successful provider authorization.

Ordinary credential enrollment and organization Search source approval are separate capabilities. A paused or organization-managed Search source does not itself prohibit a workspace credential for the same app. The fixture projection supplies `canAddCredential` separately from Search availability. A live adapter must obtain enrollment methods and eligible workspace members from their authorized operations, including viewer, deployment and provider gates; catalog membership alone never authorizes enrollment or sharing.

New skill, MCP, sharing and credential editor interactions are UI work. Their example records are loaded only through the server fixture flag and edited in the product session. Skills and MCPs are shown only in fixture mode until their live data adapters exist. Live Apps and Credentials render only data and actions supplied by an existing authorized operation. They must not substitute fixture records when a request is loading, denied, unavailable or failed. Sharing controls in an example are not permission enforcement, and creating a local example must not call a real credential, secret or policy mutation.

The custom Slack bot connection keeps its provider-specific setup in `slack-bot-connection/`: workspace choice, bot identity, generated capability choices, optional slash commands, Slack setup instructions, bot token and signing secret. Reconnect preserves the credential and workspace identity and does not edit the existing manifest. Secret inputs stay inside the mounted dialog and are cleared before its metadata-only callback or dismissal. A deployable app manifest and creation link require an authorized service to reserve the credential ID and supply public callback URLs; the fixture flow shows the setup guide and permission review without fabricating those URLs or claiming an installation succeeded.

The organization center is the canonical destination. Workspace navigation resolves the workspace host and the viewer's organization eligibility before linking or redirecting there; it never uses the session's unrelated active organization or silently changes credential scope. Preserve the existing route for viewers who cannot use the organization center, rather than trapping them behind an unavailable page. Paper references and historical documentation do not justify another Platform workspace management surface. The browser and Electron use the same renderer.

## Verification

Check destination navigation and browser history, search and empty results, sort/filter controls, create/edit/cancel flows, personal/shared grouping, dropdown placement and keyboard dismissal. Verify long names, multiple usage avatars, empty and stress data, narrow and intermediate widths, dark theme and real overflow fades. Fixture-off output must contain no sample people, credentials or shared resources. Existing live Apps detail and connection behavior must remain reachable.

For custom Slack bots, check required workspace/name fields, all generated capability choices, slash-command uniqueness and limits, back navigation, masked token entry, reconnect ownership, and clean secret fields after cancellation or submission. The fixture callback may receive only display metadata; no token or signing secret may enter session state, storage, a request, or a success notice.

Run the Platform design audit, type check, build and browser checks from the [README](../README.md). The static audit enforces styling and ownership boundaries and unused variants. Review independently that every new shared visual variant has two real consumers and that custom feature anatomy uses an established layout rhythm; a numeric JSX count cannot establish those design decisions.
