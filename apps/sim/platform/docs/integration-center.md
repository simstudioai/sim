# Integration center

`/integrations` at the organization root is the member-facing management surface for Apps, Skills, MCPs and Credentials. Home and eligible organization workspace entry points navigate here rather than mounting another copy. A standalone workspace, or a viewer without the organization's Search access, retains the existing workspace credential route until an authorized replacement exists. Organization approval and source administration remain in Settings. Entering from a workspace must not silently turn a personal credential into an organization or workspace credential.

## Product structure

| Destination | Content |
| --- | --- |
| Apps | Connected apps first, then available apps, using one All/Connected/Available/Categories submenu filter. Provider names and descriptions come from existing catalog metadata. Member credentials retain their provider detail routes. |
| Skills | Shared and Personal sections. A skill has a name, description and instructions, with ownership shown separately from its content. |
| MCPs | Shared and Personal sections for custom servers. Connection details belong to the server, not a fabricated provider catalog. |
| Credentials | Shared and Personal sections for named credentials and secrets. Show access in the list and ownership in the detail or editor, without exposing a secret in a list. |

Keep the heading, description, reading column and major gaps aligned with Home. DestinationTabs and the compact control bar follow the Platform Workspaces anatomy in Paper. Search sits at the start of the control bar; destination-specific sorting, filtering and create actions sit at the end. The Apps filter uses All, Connected, Available and Categories with a nested category list. Status and category are mutually exclusive and persist in the URL. Other destinations use All, Shared and Personal. These choices use ChoiceMenu, the exact Home period owner with a compact quiet trigger. Select/SelectField belong to the editor's form fields, not this toolbar. The title-to-description gap is 3px, matching Home. Measure 24px from the description to the tab surfaces, 12px from tabs to the control bar, and 24px from that bar to the first group heading. The tab lane has no extra vertical padding. Group headings sit 16px above their first row, matching Home Email and attention. Tabs and sibling rows use the sidebar’s 2px list gap; leading marks and copy use the shared 8px gap. Keep the tab surfaces inside the reading-column text edge, as Home does with Build/Search. The quiet search, trailing toolbar controls and list hover surfaces retain the shared 8px outer inset on both sides. Categories and ownership sections live in the content, not as another nested tab system. Empty results sit at the normal section-title edge immediately below the controls.

The route entry stays thin. `integrations/_components/integration-center/` owns the frame and destination composition. `resource-list/` and `resource-editor/` own the feature's list content and editor fields. Reuse EMCN DestinationTabs, SearchField, ActivityRow, Avatar, Button, Menu, Modal and Field owners. Base UI supplies complex behavior inside EMCN; product code supplies data and callbacks. Leading marks align with the first line, trailing people and actions center against the whole row, and lists use the same shared rhythm as Home email and notification rows. App rows end with at most three profile photos and a passive +N count before their navigation chevron. Individual photos reveal names on hover; the count opens nothing. Details keep only title and description in the heading. A static idea card follows; its usage/actions bar shows a natural-language line such as “Used by Nina Patel and 13 others.” Skills use the slash glyph; credential keys share the central key geometry. Reconnection stays an account action, without an extra list status.

## Data and access

Apps retain the existing [member inventory and credential contract](organization-integrations.md). A connected account or an organization-approved provider does not prove that its credential is shared. Usage avatars and counts require an authorized roster projection; do not derive organization usage from the viewer's personal accounts or expose another member's credential label.

The full workspace app catalog is projected at generation time from existing public block metadata, suggested skills, templates and provider connection definitions. The fixture index receives compact summaries; the server sends example copy, instructions, prompts and enrollment fields only for the selected detail. The metadata audit detects upstream drift. An app's generic `authType` is not a connection form: expose only methods present in the canonical provider definitions. Live inventory continues to come from its authorized operation.

## App and credential details

App details follow one sequence: title/description, static illustrated idea, usage/actions bar, Connected credentials, Skills and Agent templates. The bar places usage at the start and Docs / Connect integration at the end, wrapping on narrow screens. Actions for one credential stay with that record. Skills use slash-leading ActivityRows; templates use leading integration-artwork stacks. Templates paginate eight at a time in the page flow without an inner scroll area. Catalog Actions/Triggers and informational Search access lists are omitted; genuine editable tool policies remain on eligible credential details.

The idea card uses one Fireflies-inspired Sim-world illustration for this pilot, with each provider’s own mark and two-sentence example in HTML. It is a static illustration, not an editable composer. Its width and overflow align with Home’s input. Light/dark treatments keep the copy readable. Additional provider-specific artwork is deferred until this pilot is reviewed.

Credentials retain their canonical ID across provider families. Editing a Google service account through Gmail updates the same record shown through Calendar and Drive. A credential detail starts with its view-only credential ID, then editable display name and textarea description. Save/Cancel appears while dirty. Connected identity, immutable host/environment, provider method and effective access remain available without creating a third header line. Names and descriptions follow existing limits; secrets never enter lists or session metadata. Personal tokens have no sharing controls. Workspace credentials retain a named workspace and effective admin/member roles; organization-managed records retain their separate managed scope. Usage avatars are not permission evidence.

Admin controls follow the existing credential contract: edit description/name, reconnect, disconnect and share with eligible members of its owning scope. Effective workspace-admin access cannot be removed or demoted here. Keep the last active explicit administrator protected. A member may leave an explicit share when those constraints permit. Preserve pending and revoked member states. UI examples demonstrate these distinctions; authorized application operations must enforce them when the data seam is implemented.

Connection modals start with display name and description, retain required method-specific fields, and show permissions as an icon-led list within a bounded scroll viewport. They have no Docs link. Multiple methods open the menu before the form; a single method opens its form directly. Fireflies enrollment is projected from canonical managed-MCP metadata, not the catalog’s generic auth label. Connection methods preserve their actual requirements: OAuth scopes and provider environments, personal tokens, service-account fields, Google JSON, provider-specific client credentials and custom Slack bots. New enrollment in the organization center has no workspace selection. Shareable credentials retain an ordinary organization scope and initially grant access only to the connector as an explicit administrator. Sharing adds selected organization members without changing credential identity or scope; no organization-wide grant is implied. Personal/Shared groups reflect active or pending access to other members. Existing workspace and organization-managed scopes stay unchanged; owner-only tokens remain personal and unshareable. Reconnect preserves the credential ID and immutable provider host/environment. Transient secrets are cleared on close and after the metadata-only callback succeeds, with no storage or network mutation in fixture mode. A local metadata record does not imply successful provider authorization.

Ordinary credential enrollment and organization Search source approval are separate capabilities. A paused or organization-managed Search source does not itself prohibit a workspace credential for the same app. The fixture projection supplies `canAddCredential` separately from Search availability. A live adapter must obtain enrollment methods and eligible members of the owning scope from their authorized operations, including viewer, deployment and provider gates; catalog membership alone never authorizes enrollment or sharing.

New skill, MCP, sharing and credential editor interactions are UI work. Their example records are loaded only through the server fixture flag and edited in the product session. Skills and MCPs are shown only in fixture mode until their live data adapters exist. Live Apps and Credentials render only data and actions supplied by an existing authorized operation. They must not substitute fixture records when a request is loading, denied, unavailable or failed. Sharing controls in an example are not permission enforcement, and creating a local example must not call a real credential, secret or policy mutation.

The custom Slack bot connection keeps its provider-specific setup in `slack-bot-connection/`: bot identity, generated capability choices, optional slash commands, Slack setup instructions, bot token and signing secret. Reconnect preserves the credential and workspace identity and does not edit the existing manifest. Secret inputs stay inside the mounted dialog and are cleared after its metadata-only callback succeeds or on dismissal. A deployable app manifest and creation link require an authorized service to reserve the credential ID and supply public callback URLs; the fixture flow shows the setup guide and permission review without fabricating those URLs or claiming an installation succeeded.

The organization center is the canonical destination. Workspace navigation resolves the workspace host and the viewer's organization eligibility before linking or redirecting there; it never uses the session's unrelated active organization or silently changes credential scope. Preserve the existing route for viewers who cannot use the organization center, rather than trapping them behind an unavailable page. Paper references and historical documentation do not justify another Platform workspace management surface. The browser and Electron use the same renderer.

## Verification

Check destination navigation and browser history, search and empty results, sort/filter controls, create/edit/cancel flows, personal/shared grouping, dropdown placement and keyboard dismissal. Verify long names, multiple usage avatars, empty and stress data, narrow and intermediate widths, dark theme and real overflow fades. Fixture-off output must contain no sample people, credentials or shared resources. Existing live Apps detail and connection behavior must remain reachable.

For custom Slack bots, check required name fields, all generated capability choices, slash-command uniqueness and limits, back navigation, masked token entry, reconnect ownership, and clean secret fields after cancellation or submission. The fixture callback may receive only display metadata; no token or signing secret may enter session state, storage, a request, or a success notice.

Run the Platform design audit, type check, build and browser checks from the [README](../README.md). The static audit enforces styling and ownership boundaries and unused variants. Review independently that every new shared visual variant has two real consumers and that custom feature anatomy uses an established layout rhythm; a numeric JSX count cannot establish those design decisions.
