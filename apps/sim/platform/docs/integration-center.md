# Integration center

`/integrations` at the organization root is the member-facing management surface for Apps, Skills, MCPs and Credentials. Home and eligible organization workspace entry points navigate here rather than mounting another copy. An organization without member-scoped accounts, personal ones included, serves the same page over the viewer's workspace credentials and skills, one workspace at a time (`workspace` in the URL): the apps the workspace's integration access policy allows, judged on the server, connected through the shared OAuth and service-account dialogs or GitLab's personal token form. Apps the permission group withholds but lets the viewer request list as Restricted and open the shared access request dialog. Only the member-scoped parts (Search sources, connected accounts and their tool permissions, Generic Secrets, credential groups) stay Enterprise. Organization approval and source administration remain in Settings. Entering from a workspace must not silently turn a personal credential into an organization or workspace credential.

## Product structure

| Destination | Content |
| --- | --- |
| Apps | Connected apps first, then available apps, using one All/Connected/Available/Categories submenu filter. Provider names and descriptions come from existing catalog metadata. Member credentials retain their provider detail routes. |
| Skills | Shared and Personal sections. A skill has a name, description and instructions, with ownership shown separately from its content. |
| MCPs | Shared and Personal sections for custom servers. Connection details belong to the server, not a fabricated provider catalog. |
| Credentials | Shared and Personal sections for manual secrets and provider credentials that require secret input. OAuth and managed-MCP OAuth connections remain under Apps and never appear here. Show access in the list and ownership in the detail or editor, without exposing a secret in a list. |

## Data and access

Apps retain the existing [member inventory and credential contract](organization-integrations.md). A connected account or an organization-approved provider does not prove that its credential is shared. Usage avatars and counts require an authorized roster projection; do not derive organization usage from the viewer's personal accounts or expose another member's credential label.

The full workspace app catalog is projected at generation time from existing public block metadata, suggested skills, templates and provider connection definitions. The fixture index receives compact summaries; the server sends example copy, instructions, prompts and enrollment fields only for the selected detail. The metadata audit detects upstream drift. An app's generic `authType` is not a connection form: expose only methods present in the canonical provider definitions. Live inventory continues to come from its authorized operation. Its current account projection supplies no usage people, access roster or shared-credential metadata; the UI must not infer those from account labels or organization membership. Counts cover exactly the authorized accounts supplied. An unavailable live access roster remains an unavailable view, not an invented owner or grant.

App details follow one sequence: title/description, illustrated idea, usage/actions bar, Connected credentials, Skills and Agent templates. The bar places available-app usage at the start and Docs / Connect integration at the end, wrapping on narrow screens. Without an OAuth method, the primary action is Create credential. Every fixture app also offers manual credential creation; canonical provider-specific methods retain their required fields. Credential actions live beside the selected credential’s Details/Access tabs as compact quiet Replace value, Reconnect and Delete credential/Disconnect buttons when applicable. Delete and Disconnect use the shared destructive hover treatment, matching destructive menu rows; no standalone ellipsis row separates the heading from the tabs. Navigating rows have no ellipsis or action after their chevron. Connect integration uses the bordered, elevated secondary button for both single-method and menu triggers. Skills use slash-leading ActivityRows; templates use leading integration-artwork stacks. All templates remain in the page flow without pagination or an inner scroll area. Suggested skill instructions are editable before adding, using the large default textarea size. An installed example loads its saved instructions for editing, with Save changes and a separate destructive Remove from Skills action and confirmation; it can be added again after removal. Installed examples retain their provider/name source identity when a member changes their instructions or renames them, so editing does not offer duplicate installation. Catalog Actions/Triggers and informational Search access lists are omitted; genuine editable tool policies remain on eligible credential details.

The idea card uses one monochrome Sim-world meeting illustration for this pilot, with each provider’s own mark and two-sentence example in HTML. The artwork continues across the full borderless surface. A borderless MessageBubble using the existing floating glass fill and blur, without a top-edge highlight, sits in the center with a two-line preview and no arrow action; its hover and press use the shared neutral fills. The full prompt stays available when selected, including text clipped by the narrow preview. Agent templates perform the same full-prompt handoff rather than opening a read-only preview. Its width and overflow align with Home’s input. Light/dark treatments keep the copy readable. Additional provider-specific artwork is deferred until this pilot is reviewed.

Credentials retain their canonical ID across provider families. Editing a Google service account through Gmail updates the same record shown through Calendar and Drive. Credential details always include Details and Access tabs, plus Permissions when tool controls exist. Connected identity, immutable host/environment and effective access remain available without a redundant method/scope text stack. Omit “MCP connection,” “Only you,” and standalone service-account/workspace badges; provider requirements stay in the connection flow and workspace access boundaries stay in the access section. Names and descriptions follow existing limits; secrets never enter lists or session metadata. Personal tokens have an Access tab with their owner and no sharing controls. Workspace credentials retain a named workspace and effective admin/member roles; organization-managed records retain their separate managed scope. Usage avatars are not permission evidence.

Access uses an inline eligible-people and role form above a DataTable with People/Invitations tabs, search, role filter, name sorting and selection. Tables and tabs use Platform typography, insets and controls, rather than an external table theme. Name, email and role columns retain their positions across empty, filtered and populated states. Names and emails use separate columns where space permits, combine into a wrapping identity on compact layouts, and retain readable role controls beneath that identity when enlarged text requires it. Fixed minimum widths must not create horizontal scrolling; select-all and independent row actions stay visible. The checkbox, inline avatar, text and role controls center within each row, including enlarged text. The action lane remains reserved with no rows. The selection count and Change access / Remove access controls appear before the trailing filter/sort group only with a nonempty selection; Invitations uses Cancel invitations. At zero selection the group remains invisible and inert in its reserved space, so the sort control and table stay in place. There is no Clear selection action; checkboxes deselect rows without shifting the table. Changing a filter or tab clears selection; bulk changes act only on visible eligible selections and evaluate the entire resulting membership against the active explicit-admin floor. Pending grants do not replace an active administrator. Workspace and organization admin inheritance is displayed only when the credential metadata explicitly supplies it. Inherited access cannot be edited or removed here, and never implies organization-wide access to a new private connection. The old workspace-limitation paragraph is omitted.

Admin controls follow the existing credential contract: edit description/name, reconnect, disconnect and share with eligible members of its owning scope. Effective workspace-admin and organization-admin access cannot be removed or demoted here. Keep the last active explicit administrator protected. A member may leave an explicit share when those constraints permit. Preserve pending and revoked member states. UI examples demonstrate these distinctions; authorized application operations must enforce them when the data seam is implemented.

Protected selection checkboxes explain their restriction on hover, keyboard focus and touch using the same policy reason as their role and removal actions. Distinguish inherited workspace/organization administration from the last explicit administrator, and explain when another administrator must be appointed. Bulk removal explains the administrator floor; an exhausted invitation picker explains that no additional people are available. These hints do not enable restricted operations.

Connection modals start with display name and description, retain required method-specific fields, and show permissions as a grouped dot list within a scroll viewport capped at 192px or 30% of the viewport height, whichever is smaller. Longer lists, including 16 or more permissions, scroll independently beneath the heading. They have no Docs link. Multiple methods open the menu before the form; a single method opens its form directly. Fireflies enrollment is projected from canonical managed-MCP metadata, not the catalog’s generic auth label. Connection methods preserve their actual requirements: OAuth scopes and provider environments, personal tokens, service-account fields, Google JSON, provider-specific client credentials and custom Slack bots. New enrollment in the organization center has no workspace selection. Shareable credentials retain an ordinary organization scope and initially grant access only to the connector as an explicit administrator. Sharing adds selected organization members without changing credential identity or scope; no organization-wide grant is implied. Personal/Shared groups reflect active or pending access to other members. Existing workspace and organization-managed scopes stay unchanged; owner-only tokens remain personal and unshareable. Reconnect preserves the credential ID and immutable provider host/environment. Transient secrets are cleared on close and after the metadata-only callback succeeds, with no storage or network mutation in fixture mode. A local metadata record does not imply successful provider authorization.

Ordinary credential enrollment and organization Search source approval are separate capabilities. A paused or organization-managed Search source does not itself prohibit a workspace credential for the same app. The fixture projection supplies `canAddCredential` separately from Search availability. A live adapter must obtain enrollment methods and eligible members of the owning scope from their authorized operations, including viewer, deployment and provider gates; catalog membership alone never authorizes enrollment or sharing.

Example records load only in a fixture build (`SIM_PLATFORM_FIXTURES=1` at build time) and are edited in the product session. Live Apps, Skills, MCPs and Credentials render only data and actions supplied by an existing authorized operation. They must not substitute fixture records when a request is loading, denied, unavailable or failed. Sharing controls in an example are not permission enforcement, and creating a local example must not call a real credential, secret or policy mutation.

The custom Slack bot connection keeps its provider-specific setup in `slack-bot-connection/`: bot identity, generated capability choices, optional slash commands, Slack setup instructions, bot token and signing secret. Reconnect preserves the credential and workspace identity and does not edit the existing manifest. Secret inputs stay inside the mounted dialog and are cleared after its metadata-only callback succeeds or on dismissal. A deployable app manifest and creation link require an authorized service to reserve the credential ID and supply public callback URLs; the fixture flow shows the setup guide and permission review without fabricating those URLs or claiming an installation succeeded.

On live data the center serves Apps, Skills, MCPs and Credentials, the same way for every organization. Skills and MCP servers are workspace-scoped, as legacy scopes them: the workspace choice in the control bar (`workspace` in the URL) picks whose are listed. Skills are created, edited and shared with editors here, and built-in skills are read-only; Connect MCP and an MCP row open the workspace's MCP Settings.

The organization center is the canonical destination. Workspace navigation resolves the workspace host and the viewer's organization eligibility before linking or redirecting there; it never uses the session's unrelated active organization or silently changes credential scope. Every viewer can use the organization center: legacy workspace Integrations and Skills URLs redirect there with their workspace. Paper references and historical documentation do not justify another Platform workspace management surface. The browser and Electron use the same renderer.

## Verification

Check destination navigation and browser history, search and empty results, sort/filter controls, create/edit/cancel flows, personal/shared grouping, dropdown placement and keyboard dismissal. Verify long names, multiple usage avatars, empty and stress data, narrow and intermediate widths, dark theme and real overflow fades. Fixture-off output must contain no sample people, credentials or shared resources. Existing live Apps detail and connection behavior must remain reachable.

For custom Slack bots, check required name fields, all generated capability choices, slash-command uniqueness and limits, back navigation, masked token entry, reconnect ownership, and clean secret fields after cancellation or submission. The fixture callback may receive only display metadata; no token or signing secret may enter session state, storage, a request, or a success notice.

Run the Platform design audit, type check, build and browser checks from the [README](../README.md). The static audit enforces styling and ownership boundaries and unused variants. EMCN is frozen, so the center composes existing components and adds no variant. Review independently that custom feature anatomy uses an established layout rhythm; a numeric JSX count cannot establish that.

## Manual secrets and modal composition

Manual credentials can be linked to any fixture app or remain unlinked. Supported types are generic secret, API key, access token, refresh token, client secret, PEM private key, service-account JSON, and username/password. Switching types clears the mounted value fields. JSON and PEM receive format validation; paired credentials require both values. This is storage metadata, not a claim that any app supports every authentication scheme, automatic token refresh, or successful authorization. New records start private with the creator as explicit administrator. The Access tab adds selected people afterward and retains the same ID and organization scope. Replacement and cancellation clear transient values; no value, username/password pair, key material or token reaches fixture session state or a network write.

Linked manual secrets appear under the app’s Connected credentials and in Credentials; connected counts include authorized shared records and these linked secrets. Directory rows use their provider mark when linked. Existing OAuth accounts remain reachable under Apps; the directory classification never disconnects or deletes them. Linked credential detail headings use the app’s provider mark, matching the app context (Gmail shows Gmail even for a shared Google credential). Only unlinked manual secrets use the secret/key icon. A credential opened from the Credentials directory returns there with its filters and sorting intact; one opened from an app returns to that app. The URL records that origin so refresh and browser history preserve it. Standalone manual details use Back to Credentials.

Modals compose standard fields instead of feature-specific control chrome. Full-width uploads center their prompt, while compact image fields support previews and removal. ListField supplies the requested-permission headings, bullets and scroll ceiling. DetailsField supplies labeled static information, and RecipientField supplies invitation parsing, tags and keyboard editing. Skills retain their editable large instruction textarea before adding; a table is reserved for real tabular content.
