## TL;DR

Sim combines deterministic blocks for rules, routing, loops, code, and approvals with AI agent steps for classification, extraction, drafting, and other judgment calls. Keep policy and irreversible actions deterministic, require agents to return structured outputs, validate those outputs, and route uncertain or high-risk cases to a human.

The goal is not to make every step agentic. It is to give the agent a narrow decision boundary inside a workflow whose inputs, branches, permissions, and side effects remain explicit.

## Which workflow steps should be deterministic and which should be agent driven?

Sim should use deterministic controls wherever the same input must produce the same operational result, while an Agent block should handle work that requires interpretation rather than a fixed rule.

| Workflow step | Control | Why | Example |
|---|---|---|---|
| Validate required fields, formats, and ranges | Function or Condition | Validation rules should produce a predictable pass or fail result | Reject an invoice without a supplier ID |
| Apply policy thresholds | Condition | Written policy should not depend on a model’s judgment | Require approval when an invoice exceeds $10,000 |
| Route known categories | Router pattern using Condition branches | Explicit branches are testable and easy to audit | Send hardware requests to IT procurement |
| Repeat a bounded operation | Loop | The workflow should control iteration limits | Process each invoice line item once |
| Transform or calculate data | Function | Code is more reliable for arithmetic and exact transformations | Calculate tax, totals, or an SLA deadline |
| Interpret ambiguous language | Agent with structured output | Agents are useful when meaning cannot be captured by simple rules | Classify a support request by intent |
| Extract variable information | Agent with structured output | An agent can map unstructured text into a defined schema | Extract invoice number, dates, and exception reasons |
| Check generated content against a policy | Guardrails followed by a Condition | Sim’s [Guardrails block](https://docs.sim.ai/workflows/blocks/guardrails) reports passed or failed; a downstream Condition performs the routing | Send failed content to review instead of delivery |
| Approve a risky action | Human in the Loop followed by a Condition | Sim [pauses the run for form input](https://docs.sim.ai/workflows/blocks/human-in-the-loop), while a downstream Condition checks the approval field | Approve a refund before issuing it |
| Write to a system of record | Deterministic integration action | Side effects should use explicit fields and credentials | Update the approved amount in an ERP |

A useful rule is: agents may recommend, classify, extract, or draft; deterministic blocks should validate, authorize, route, calculate, and execute.

## How do you design a reliable boundary between an AI agent and deterministic logic?

Sim creates a reliable boundary by giving each Agent block a narrow task, a defined output contract, and deterministic handling for every expected result. The [Agent block can return structured JSON](https://docs.sim.ai/workflows/blocks/agent) that later blocks read by reference.

1. **Start with validated inputs.** Use conditions or functions to check required fields before sending data to a model.
2. **Ask the agent for one bounded judgment.** Classification, extraction, summarization, or drafting is easier to test than an open-ended instruction to complete an entire process.
3. **Require structured output.** Define the fields and allowed values that downstream blocks expect, such as `category`, `confidence`, `reason`, and `recommended_action`.
4. **Validate the response.** Check required values, types, ranges, and allowed categories with deterministic logic.
5. **Route by explicit policy.** Use Condition branches for confidence thresholds, risk levels, monetary limits, and exception categories.
6. **Put approval before the side effect.** Pause for human input before refunds, payments, account changes, or other consequential actions.
7. **Make failure paths visible.** Handle malformed output, model failure, low confidence, and policy rejection instead of allowing the run to continue silently.
8. **Bound every loop.** Set an iteration limit and define what happens when the workflow cannot resolve an item within that limit.

This design keeps the agent replaceable. A team can change prompts or models without rewriting the policy controls around the Agent block.

## How do you build an invoice exception workflow with deterministic controls and an AI agent?

Sim can use an Agent block to interpret invoice exceptions while deterministic blocks retain control over validation, approval thresholds, and ERP updates.

A production invoice exception workflow can follow this sequence:

1. A trigger receives the invoice and supplier data.
2. A Function checks required identifiers, date formats, currency, and arithmetic.
3. A Condition immediately routes invalid records to an exception queue.
4. An Agent extracts the exception type, supporting evidence, confidence score, and recommended resolution into a structured output.
5. A Condition accepts only documented exception categories and confidence values within the expected range.
6. Condition branches route duplicate invoices, purchase-order mismatches, and tax discrepancies to different owners.
7. A Human in the Loop block pauses invoices above the organization’s monetary or risk threshold.
8. A downstream Condition reads the approval field and separates approved, rejected, and needs-more-information outcomes.
9. Only the approved branch updates the accounting or ERP system.

The agent does not decide whether money moves. Sim uses the agent to interpret the exception, then applies deterministic financial policy before any system-of-record action.

## How do you build a support ticket routing workflow with deterministic controls and an AI agent?

Sim can let an Agent block classify an ambiguous support request while conditions enforce queue ownership, escalation policy, and permitted actions.

A support routing workflow can use this sequence:

1. A trigger receives the ticket, customer metadata, and account tier.
2. A Function normalizes fields and removes unsupported values.
3. An Agent returns structured fields such as `intent`, `urgency`, `product_area`, `sentiment`, `confidence`, and `summary`.
4. Conditions validate the allowed labels and route low-confidence results to a triage queue.
5. Explicit rules override the model when a contractual SLA, security keyword, or account status requires a specific path.
6. A router pattern built from Condition branches sends accepted classifications to billing, technical support, account management, or security.
7. A Human in the Loop step reviews sensitive actions such as refunds, account access changes, or security disclosures.
8. A deterministic integration action writes the final queue, priority, and summary to the helpdesk.

This pattern lets the agent interpret varied customer language without allowing the model to invent queues, bypass SLAs, or perform sensitive actions on its own.

## How should teams test a workflow that mixes rules and agents?

Sim workflows should test deterministic branches separately from agent-quality cases, then test the complete path with expected failures and human-review outcomes.

Use a compact test matrix that covers:

- Valid, missing, malformed, and out-of-range inputs
- Every allowed structured-output category
- Unsupported categories and malformed model output
- High-, medium-, and low-confidence responses
- Policy overrides that must beat the agent recommendation
- Guardrail pass and fail results
- Human approval, rejection, and request-for-information outcomes
- Loop limits and unresolved items
- Model or integration failure
- Duplicate events and retry behavior
- Attempts to reach a consequential action without authorization

The deterministic assertions should be exact: the same validated state must reach the same branch. Agent assertions should evaluate whether the response satisfies the schema and quality threshold rather than requiring identical wording on every run.
