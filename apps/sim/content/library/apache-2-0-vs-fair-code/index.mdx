**As of October 2026, the self-hostable AI agent builders and automation platforms with a permissive Apache 2.0 or MIT license are Sim (Apache 2.0 core), Langflow (MIT), Activepieces (MIT core), Kestra (Apache 2.0), Node-RED (Apache 2.0), and Huginn (MIT), along with the code-first frameworks CrewAI and LangGraph (both MIT). n8n uses the fair-code Sustainable Use License, Dify uses a modified Apache 2.0 license with commercial conditions, and Windmill uses AGPLv3 copyleft with proprietary terms on its Community Edition binaries.**

**Apache 2.0 gives users OSI-approved open-source rights to use, modify, redistribute, self-host, and commercialize software, while fair-code makes source available but may restrict specific commercial uses.**

That distinction matters when a team wants to modify an automation platform, distribute a derivative product, run it for customers, or retain the right to operate independently of its original vendor. Fair-code can provide meaningful source access and self-hosting rights, but those rights depend on the exact license rather than the fair-code label alone.

Sim is the open-source AI workspace where teams build, deploy, and manage AI agents.

[Sim's core code](https://github.com/simstudioai/sim/blob/main/LICENSE) uses Apache License 2.0. Features in `apps/sim/ee`, including built-in white-labeling, use a [separate Sim Enterprise License](https://github.com/simstudioai/sim/blob/main/apps/sim/ee/LICENSE) that permits development, testing, and internal non-production use; production use requires an active Sim Enterprise subscription, and modification and redistribution are not permitted. As of October 2026, [n8n](https://docs.n8n.io/n8n-community-license) uses its Sustainable Use License, a source-available fair-code license that permits internal business use but restricts certain customer-facing commercial uses.

This article provides a practical comparison, not legal advice. Have qualified counsel review the license for a production use case when the planned activity is commercially significant.

## TL;DR

- **Apache 2.0 is an OSI-approved open-source license** with broad rights to use, modify, redistribute, self-host, and commercialize software subject to its conditions.
- **Fair-code is an umbrella approach, not one standardized license.** Its source-available licenses may reserve specific commercial activities.
- **As of October 2026, n8n's Sustainable Use License permits internal business use but not charging customers to access hosted n8n without a separate agreement.**
- **Sim's Apache-licensed code supports internal self-hosting, customer-facing products, and managed services** without a separate license solely because the deployment is commercial; production use of separately licensed Enterprise features requires a valid subscription.
- **"Open source" on a product page is not enough for a legal review.** Check the license of every directory you will run: Sim, Activepieces, and Flowise keep enterprise code under separate commercial licenses, and Dify adds conditions to Apache 2.0.

## What is Apache 2.0?

[Apache 2.0](https://www.apache.org/licenses/LICENSE-2.0) is an OSI-approved open-source license that permits commercial use, modification, distribution, sublicensing, and private use subject to its notice and attribution conditions.

The license also includes an express patent grant from contributors. Distributors must provide a copy of the license, retain applicable notices, identify modified files, and handle any NOTICE file as the license requires. Apache 2.0 does not require modified source code to be published, and it does not grant trademark rights.

## What is fair-code licensing?

[Fair-code](https://faircode.io/) is a source-available licensing approach that permits some uses of visible source code while reserving or restricting other uses, commonly including commercial hosting or resale.

Fair-code is not one standardized license. The permissions depend on the exact license text used by a vendor, so the label alone cannot answer whether a company may redistribute the code, offer it as a service, or embed it in a commercial product. A fair-code product can provide meaningful source access and permit internal self-hosting without meeting the Open Source Initiative's definition of open source.

## What is the difference between Apache 2.0 and fair-code licensing?

**Apache 2.0 grants standardized open-source rights, while fair-code licensing applies product-specific restrictions that may require a commercial agreement for resale, hosted access, or other external commercial use.**

Apache 2.0 is an [OSI approved open source license](https://opensource.org/license/apache-2-0). Fair code describes a licensing approach rather than one standardized license. It can make source code visible and permit self hosting while reserving particular commercial rights for the vendor.

## Key facts at a glance

Sim's core is licensed under Apache 2.0 and can be self hosted, modified, and redistributed under that license. Code in `apps/sim/ee` has separate production and redistribution restrictions under the [Sim Enterprise License](https://github.com/simstudioai/sim/blob/main/apps/sim/ee/LICENSE).

As of October 2026, n8n is source available under the [Sustainable Use License](https://docs.n8n.io/n8n-community-license). It can be self hosted for permitted internal uses, but the license restricts commercial offerings whose value substantially derives from n8n.

Apache 2.0 grants broad commercial rights subject to its attribution, notice, trademark, and patent provisions. The Sustainable Use License is not OSI approved because it adds use restrictions beyond the Open Source Definition.

## Can Apache 2.0 software be modified and redistributed?

**Apache 2.0 permits both modification and redistribution in source or object form when its conditions are followed.**

Section 4 of the [Apache License 2.0](https://www.apache.org/licenses/LICENSE-2.0) requires a distributor to:

1. Give recipients a copy of the Apache License 2.0.
2. Add prominent notices to modified files stating that the files were changed.
3. Retain applicable copyright, patent, trademark, and attribution notices from the original source.
4. Include the relevant attribution notices from a NOTICE file when the original work contains one.

Apache 2.0 is permissive rather than copyleft. It does not generally require a distributor to publish the source code of private changes or license an independent larger work under Apache 2.0. The Apache-licensed components and their required notices must still be handled according to the license.

Under [n8n's Sustainable Use License](https://docs.n8n.io/n8n-community-license), redistribution is permitted only within the license's boundaries, including that providing the software to others must be free of charge and for noncommercial purposes. A company planning to sell, sublicense, white-label, or provide n8n to customers should obtain a written determination from n8n or legal counsel rather than treating source availability as unrestricted redistribution permission.

## Can Apache 2.0 software be used in a commercial product?

**Apache 2.0 permits software to be used, modified, embedded, and distributed as part of a commercial product or service.**

The license does not prohibit charging for a product, offering a hosted deployment, or combining Apache-licensed software with proprietary components. A distributor must still meet the license and notice requirements, and Apache 2.0 does not grant rights to the project's trademarks.

For Sim, this means the Apache-licensed code can support internal deployments, customized products, commercial integrations, and hosted services without requiring a separate license merely because the use is commercial. Features in `apps/sim/ee` are separately licensed, require an Enterprise subscription for production use, and may not be redistributed.

## Can fair-code software be used commercially?

**Fair-code software may permit internal commercial use while restricting resale, white-labeling, or paid access to a hosted version.**

The result depends on the specific fair-code license. Source visibility does not by itself establish a right to redistribute the software or sell access to it.

As of October 2026, [n8n's Sustainable Use License documentation](https://docs.n8n.io/n8n-community-license) allows use for internal business purposes and certain other permitted activities. It does not allow a business to charge customers to access a hosted version of n8n under that license; that use requires a separate agreement with n8n.

This does not mean n8n cannot be used by a commercial company. As of October 2026, it means the intended deployment model matters: automating a company's own operations is different from exposing n8n's functionality to paying customers.

## Can Apache 2.0 and fair-code software be self-hosted?

**Apache 2.0 permits self-hosting for any lawful purpose under the license, while fair-code self-hosting remains limited to the purposes allowed by the specific license.**

Sim's Apache-licensed code can be self-hosted for internal operations, customized deployments, customer-facing systems, or managed services. Apache 2.0 does not distinguish among those purposes. Production use of separately licensed features in `apps/sim/ee` requires a valid Enterprise subscription.

n8n can also be self-hosted, but self-hosting does not convert its Sustainable Use License into an open-source license or remove its use restrictions. As of October 2026, internal business self-hosting is permitted; charging customers to access hosted n8n is not permitted under the [Sustainable Use License](https://docs.n8n.io/n8n-community-license) without a separate agreement.

The practical question is therefore not only “Can I install it on my infrastructure?” It is also “What am I allowed to do with that installation?”

Sim offers broader self hosting freedom for its Apache 2.0 core. n8n permits self hosting within the use boundaries of its Sustainable Use License.

## What commercial risks should legal teams check before adopting an AI agent builder?

**Legal teams should check the license of every directory they will run, field-of-use and multi-tenant restrictions, copyleft network obligations, branding clauses, and whether the license can change for future versions.**

These are the clauses that most often turn an internal pilot into a commercial-licensing problem later:

1. **Open-core directories.** A permissive root LICENSE can sit beside a commercial license for an `ee/` or `enterprise/` directory. Sim, Activepieces, and Flowise all follow this pattern, so confirm which features the deployment actually uses.
2. **Field-of-use limits.** The [Open Source Definition](https://opensource.org/osd) forbids restricting use by field of endeavor. Licenses that limit use to internal business purposes, such as [n8n's Sustainable Use License](https://docs.n8n.io/n8n-community-license), are therefore not OSI-approved.
3. **Multi-tenant and hosting clauses.** [Dify's license](https://github.com/langgenius/dify/blob/main/LICENSE) requires written authorization to run a multi-tenant service, and Windmill's Community Edition binaries may not be offered as a managed service. Check these before building a customer-facing product.
4. **Copyleft obligations.** AGPLv3 code is open source, but modified versions offered over a network must make their source available to those users.
5. **Branding requirements.** Some licenses forbid removing logos or copyright notices from the user interface, which matters for white-label products.
6. **License-change risk.** A vendor can relicense future versions. Released versions keep the license they shipped with, so record the license of the exact version you deploy.
7. **Patents and trademarks.** [Apache 2.0](https://www.apache.org/licenses/LICENSE-2.0) includes an express patent grant; MIT does not mention patents. Neither license grants trademark rights.
8. **Third-party terms.** Connectors, models, SDKs, container images, templates, and dependencies can carry independent licenses.
9. **Customer access.** Hosting, managed-service, white-label, embedding, and resale rights can differ from internal-production rights.
10. **Procurement records.** Capture the exact license text, version or commit, covered directories, planned use, and notices reviewed at adoption.

This checklist is a starting point for legal review, not legal advice.

## Does Apache 2.0 reduce vendor lock-in?

**Apache 2.0 reduces licensing-based vendor lock-in because users retain broad rights to run, inspect, modify, fork, and redistribute the software without the original vendor's permission.**

Those rights give an organization more exit options if pricing, product direction, support, or hosting terms change. A team can maintain its own deployment, contract with another provider, or build on a fork while continuing to meet the license conditions.

Apache 2.0 does not eliminate every form of lock-in. Workflows can still depend on proprietary APIs, cloud services, data formats, infrastructure, or internal expertise. Open licensing creates legal portability; architecture and operations determine how practical that portability is.

Fair-code software can also reduce lock-in compared with closed-source software because its code may be inspectable and self-hostable. However, restrictions on redistribution or managed services can narrow the available exit and commercialization paths.

## Why does OSI approval matter?

OSI approval gives buyers a recognized standard for determining whether a license grants open source freedoms without restricting use by a person, organization, or field of endeavor.

Apache 2.0 meets that standard. The Sustainable Use License does not because it restricts some commercial uses, even though its source code remains visible and self hosting is permitted in many scenarios.

For engineering teams, the distinction affects forks, patches, redistribution, and long term deployment flexibility. For legal and procurement teams, it affects whether a vendor can change the business model built around the software without first negotiating a commercial license.

## Is fair code the same as open source?

Fair code is not the same as OSI-approved open source because fair-code licenses can make source code available while restricting certain commercial uses.

Fair code is a category and philosophy rather than one universal license. The applicable rights come from the specific license text used by a project. A buyer should ask which exact license and version governs the code instead of accepting “open,” “open source,” or “source available” as interchangeable labels. The [Open Source Definition](https://opensource.org/osd) requires licenses to meet criteria including free redistribution and no discrimination against fields of endeavor; Apache 2.0 and MIT meet that standard, while n8n's Sustainable Use License does not.

## Is source available the same as permissively licensed?

Source-available software is not necessarily permissively licensed because visible source code may still carry restrictions on hosting, redistribution, modification, or commercial use.

A permissive license such as Apache 2.0 or MIT grants broad rights with relatively limited conditions. A source-available license may grant only a subset of those rights. Legal teams should evaluate the operative clauses, not whether a repository is public or whether the product supports self-hosting. Dify illustrates this distinction: its [public license](https://github.com/langgenius/dify/blob/main/LICENSE) adds conditions to Apache-style terms, so a team should not treat Dify as though it used the unmodified Apache License 2.0.
