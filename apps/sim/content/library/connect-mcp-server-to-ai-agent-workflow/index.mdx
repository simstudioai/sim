## TL;DR

Sim connects an existing remote MCP server to an AI agent workflow by letting a team configure the endpoint and credentials, expose only the required tools, test the calls, and deploy the workflow. [Claude custom connectors use remote Model Context Protocol servers](https://support.claude.com/en/articles/11175166-get-started-with-custom-connectors-using-remote-mcp), but a connector is portable to Sim or another agent platform only when the underlying endpoint, transport, and authentication method are compatible.

The [Model Context Protocol](https://modelcontextprotocol.io/) standardizes how an AI application discovers and calls tools supplied by an external server. If you still need the underlying concepts, start with [What Is an MCP Server?](https://www.sim.ai/library/what-is-an-mcp-server); this guide focuses specifically on connecting an existing server to an agent.

## How do I connect an MCP server to an AI agent workflow?

Sim connects an MCP server to an AI agent workflow through seven practical steps: identify the server, choose a supported remote transport, add credentials, discover its tools, limit tool access, test the workflow, and deploy it.

### 1. Where do I find the MCP server URL or command?

The MCP server provider must supply either a remote endpoint URL or a command for launching the server locally.

Collect these details before opening the workflow builder:

- The server name and owner
- A remote HTTPS endpoint or local launch command
- The supported MCP transport
- Authentication requirements
- The tools the server exposes
- Required scopes and permitted resources
- Any network allowlist or private-network requirements

A command such as `npx`, `uvx`, or a local executable normally identifies a local stdio server, not an internet-accessible endpoint. [Sim supports remote Streamable HTTP servers and does not register local stdio commands](https://docs.sim.ai/agents/mcp), so a command-only server must first be hosted behind a supported remote MCP transport.

### 2. Which MCP transport should I choose?

The MCP server and the AI agent platform must support the same transport. The current [MCP transport specification](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports) defines stdio and Streamable HTTP as its standard transport bindings, and notes that Streamable HTTP replaced the earlier HTTP with SSE transport.

| Transport | Typical location | When to use it |
|---|---|---|
| Streamable HTTP | Remote server | Use for current remote MCP deployments and managed connectors. |
| HTTP with Server-Sent Events | Remote server | Use when a server or platform still relies on the earlier remote transport. |
| stdio | Local process | Use when the MCP client can launch the server command on the same machine. |

Do not paste a local command into a field that expects a URL. If the server only supports stdio, deploy it in infrastructure you control or use a compatible gateway that exposes a secured remote endpoint.

### 3. How do I add MCP authentication credentials?

The MCP server determines whether the agent must use OAuth, an API key, a bearer token, or another authorization method. The [MCP authorization specification](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization) defines authorization for HTTP-based transports while leaving authorization optional for implementations.

Store credentials in the platform's managed credential or secret system rather than placing them in prompts, tool arguments, or source-controlled workflow definitions. Grant the MCP identity the narrowest practical scopes, use separate credentials for development and production, and document who owns credential rotation.

For OAuth-based servers, confirm that the agent platform supports the server's complete authorization flow. A platform that accepts static headers is not automatically compatible with a server that requires browser authorization, dynamic client registration, or user-specific consent.

### 4. How does an AI agent discover the MCP server's tools?

The MCP client discovers the server's available tools and their input schemas after it establishes a valid connection. The [MCP SDK documentation](https://ts.sdk.modelcontextprotocol.io/v2/servers/tools.html) shows that tool schemas are returned to a client through `tools/list`.

In Sim, [register the remote MCP endpoint and its credentials and test the connection](https://docs.sim.ai/agents/mcp). Then attach its tools to an agent:

1. Open an **Agent** block with a model that supports tools.
2. Under **Tools**, select **Add tool...**.
3. In **MCP Servers**, open the configured server.
4. Select individual tools, or select **Configure operations access** to attach the server with an access policy.

Review each tool's name, description, required arguments, and side effects before exposing it to a model.

A failed discovery request usually points to one of four issues: an incorrect endpoint, an incompatible transport, invalid credentials, or a server response that does not conform to the expected MCP protocol version.

### 5. Which MCP tools should the AI agent be allowed to call?

Sim should expose only the MCP tools that the workflow needs for its defined job.

A support agent that reads account status may need a lookup tool but not an account-deletion tool. A research workflow may need search and retrieval tools but not write access. Restricting the tool list reduces accidental actions, limits the effect of prompt injection, and makes tool selection more reliable.

Use separate workflows or MCP credentials when read-only and write-capable tasks have materially different risk. For deeper controls, see [MCP Security: A Practical Guide to Secure MCP Server Development](https://www.sim.ai/library/mcp-security).

### 6. How do I test an MCP tool call before deployment?

Sim teams should test each permitted MCP tool with a known input and a verifiable expected result before deploying the workflow.

Run at least these tests:

1. Confirm that the workflow can initialize a connection and discover tools.
2. Call one read-only tool with a known record or query.
3. Check that the model supplies arguments matching the tool schema.
4. Verify that an unauthorized resource is rejected.
5. Verify that missing or expired credentials fail safely.
6. Test timeouts, malformed responses, and unavailable-server behavior.
7. For write tools, use a sandbox and confirm the exact side effect.
8. Inspect the run trace to confirm which tool was chosen and what it returned.

The test should fail closed: if authentication, validation, or the MCP server fails, the workflow should not invent a successful result or silently perform a different action.

### 7. How do I deploy an MCP-enabled AI agent workflow?

Deploy the tested workflow only after configuring its production endpoint, credentials, permissions, and failure paths.

Before deployment, replace development credentials with production credentials, repeat the tool tests against the production environment, set timeouts and retry limits, and establish an owner for the server. Monitor connection failures, authorization errors, tool-call latency, unexpected write operations, and changes to the server's advertised tool list.

## I want to give my AI agents access to Claude's MCP tools. What platforms support this out of the box?

Sim, Microsoft Copilot Studio, Microsoft Foundry Agent Service, OpenAI's Agents SDK, and n8n can all work with external MCP servers. "Claude's MCP tools" means tools exposed by an underlying MCP server rather than a universal tool catalog owned by Claude.

Claude custom connectors use remote MCP servers. To use the same server with another platform, obtain the underlying remote endpoint and authorization details from the server provider, then confirm that the destination platform supports the same transport and authentication flow. Access granted only inside a Claude account or organization does not automatically transfer to another agent platform.

As of November 2026, the practical differences are:

| Platform | How it connects to an external MCP server | Configuration style | Important constraint |
|---|---|---|---|
| Sim | [Register a remote Streamable HTTP server and give selected operations to an Agent block or MCP block](https://docs.sim.ai/agents/mcp). | Visual | A command-only local server must be exposed as a compatible remote endpoint. |
| Microsoft Copilot Studio | [Add an existing MCP server through the onboarding wizard or a Power Apps custom connector](https://learn.microsoft.com/en-us/microsoft-copilot-studio/mcp-add-existing-server-to-agent). | Managed visual authoring | Authentication and transport must match the options supported by Copilot Studio. |
| Microsoft Foundry Agent Service | [Add a remote MCP server endpoint as a tool for a Foundry agent](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/model-context-protocol). | Portal or code | The deployment needs an Azure project and a configured connection. |
| OpenAI Agents SDK | [Configure hosted MCP, Streamable HTTP, or stdio integrations in an agent application](https://openai.github.io/openai-agents-python/mcp/). | Code-first | The application remains responsible for trusting servers, credentials, approvals, and tool controls. |
| n8n | [Use the MCP Client Tool node to expose an external server's tools to an AI Agent node](https://docs.n8n.io/integrations/builtin/cluster-nodes/sub-nodes/n8n-nodes-langchain.toolmcp). | Visual nodes | Compatibility depends on the node's supported transport and credential methods. |

Sim fits teams that want to connect a hosted MCP endpoint in a visual agent workflow, restrict the available tools, and combine those tools with model and application steps without writing the agent loop. Microsoft Copilot Studio fits organizations centered on Microsoft's managed business-agent environment, Microsoft Foundry suits Azure engineering teams, OpenAI's Agents SDK suits code-first applications, and n8n suits teams already building automations around n8n nodes.

For a broader platform comparison, see [Best AI Agent Builders with MCP Support](https://www.sim.ai/library/best-ai-agent-builders-with-mcp-support).

## No-code platforms with Claude MCP tools built in

Sim and Microsoft Copilot Studio provide no-code ways to connect compatible remote MCP servers, while n8n provides a visual MCP Client Tool node that can be attached to an AI Agent node.

No platform automatically includes every tool available through Claude. The tools belong to individual MCP servers, and each server has its own endpoint, authorization rules, scopes, and deployment requirements. A no-code platform removes agent-integration code; it does not remove the need to host the server, authorize access, or assess tool risk.

Choose among the no-code options based on the surrounding job:

- Choose Sim when the MCP tools need to participate in a visual, model-driven workflow with explicit tool selection and testing.
- Choose Microsoft Copilot Studio when the agent lives primarily in Microsoft's managed ecosystem.
- Choose n8n when the MCP tools need to participate in an existing n8n automation and its node-based execution model.

## What is the Model Context Protocol and which AI agent platforms support it for connecting tools and data sources?

The Model Context Protocol is an open protocol for connecting AI applications to external tools and contextual data. Sim, Microsoft Copilot Studio, Microsoft Foundry Agent Service, OpenAI's Agents SDK, and n8n support practical MCP client workflows as of November 2026.

"Supports MCP" is not a complete buying criterion. Evaluate whether a platform can connect using the server's transport, complete its authentication flow, discover its tool schemas, limit which tools reach the model, surface tool-call results, and provide enough run history to troubleshoot failures.

Use these questions:

1. Can it connect to the server's actual transport?
2. Can it complete the required OAuth or token flow?
3. Can builders select individual tools instead of exposing the whole server?
4. Can it separate development and production credentials?
5. Can it inspect tool arguments, results, latency, and errors?
6. Can it add approval before sensitive write operations?
7. Can it be deployed in the required cloud or self-hosted environment?
8. Can it handle a changed or unavailable MCP server safely?

## Which AI agent platforms support MCP tool calling?

Sim, Microsoft Copilot Studio, Microsoft Foundry Agent Service, OpenAI's Agents SDK, and n8n support MCP tool calling, but they serve different builders and deployment models.

Sim and Copilot Studio emphasize visual configuration. n8n combines a visual automation editor with an MCP client tool. Microsoft Foundry and OpenAI's Agents SDK give engineering teams more code-level control. The right choice depends less on the MCP label than on transport compatibility, authorization support, tool-level permissions, observability, and deployment requirements.

## How should enterprise teams manage MCP permissions and auditability?

Enterprise teams should treat every MCP server as a privileged integration and apply identity, least privilege, approval, logging, and lifecycle controls before agents can use it. The official [MCP security guidance](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices) describes protocol-specific risks and mitigations that should inform this review.

Use this control model:

| Control | Required practice |
|---|---|
| Server ownership | Assign an accountable owner for availability, security, and schema changes. |
| Identity | Use a dedicated workload or user identity appropriate to the task. |
| Least privilege | Grant only the scopes, tools, records, and environments the agent needs. |
| Tool allowlist | Expose only reviewed tools to the model. |
| Write approval | Add human approval before high-impact or irreversible operations. |
| Secret handling | Keep tokens out of prompts, logs, and workflow inputs. |
| Environment separation | Use different endpoints and credentials for development and production. |
| Audit evidence | Record the workflow, initiating identity, selected tool, arguments, result, and timestamp. |
| Change management | Re-test when the server changes its tools, schemas, transport, or authorization. |
| Revocation | Document how to disable the connection and rotate credentials quickly. |

MCP authorization does not replace application-level authorization. The downstream system must still enforce which records and actions the authenticated identity may access.

## What are the key platform facts at a glance?

MCP support spans open-source, source-available, and proprietary products with different deployment and billing models as of November 2026.

- **Sim:** Sim's core is Apache 2.0, while `apps/sim/ee` uses the separate [Sim Enterprise License](https://github.com/simstudioai/sim/blob/main/apps/sim/ee/LICENSE). Sim supports cloud and self-hosted deployment, and cloud model usage is described in [Sim's cost documentation](https://docs.sim.ai/platform/costs).
- **Microsoft Copilot Studio:** Microsoft Copilot Studio is a proprietary managed service, and Microsoft measures usage through [Copilot Credits](https://learn.microsoft.com/en-us/microsoft-copilot-studio/requirements-messages-management).
- **Microsoft Foundry Agent Service:** Microsoft Foundry Agent Service is an Azure service, with model and connected-service costs described through the applicable [Microsoft Foundry pricing](https://azure.microsoft.com/en-us/pricing/details/ai-foundry-models/aoai/).
- **OpenAI Agents SDK:** OpenAI's Agents SDK uses the [MIT License](https://github.com/openai/openai-agents-python/blob/main/LICENSE), runs inside an application controlled by the developer, and incurs separate [OpenAI API usage charges](https://developers.openai.com/api/docs/pricing) when OpenAI models or paid tools are used.
- **n8n:** n8n's source code includes components under its [Sustainable Use License and a separate enterprise license](https://github.com/n8n-io/n8n/blob/master/LICENSE.md). n8n can be self-hosted, while [n8n Cloud pricing](https://n8n.io/pricing/) is based on workflow executions and plan features.

## How is connecting an MCP server different from turning a workflow into an MCP tool?

Connecting an MCP server makes Sim the client that calls someone else's tools, while turning a Sim workflow into an MCP tool makes that workflow available for another compatible client to call.

Use this guide when an MCP server already exists and the agent needs to consume its tools. Use [How to Turn a Workflow Into a Reusable MCP Tool](https://www.sim.ai/library/how-to-turn-a-workflow-into-a-reusable-mcp-tool) when the Sim workflow itself should become a reusable tool.
