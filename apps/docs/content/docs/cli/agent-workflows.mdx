Use [Sim CLI authentication](/cli/authentication) for shell commands. To connect
an assistant over MCP, start with the [hosted Sim MCP overview](/mcp). Its
[capability map](/mcp#choose-an-interface) explains which operations need the CLI
or HTTP API, including binary downloads.

## Discover the exact operation and credential

```sh
sim tools list --search slack
sim tools get slack_message
sim credentials list --search "Support connection"
sim --output json credentials get "$CREDENTIAL_ID"
```

Use the returned tool ID and parameter schema; do not derive IDs from an English
verb. For example, Slack sending uses `slack_message`. Supply the intended
credential ID in the tool's documented credential parameter. A workflow can use
a different credential from a direct tool call even when both are started by the
same Sim user.

`credentials get` reports the credential type/provider, stored identity metadata,
and recorded scopes with their source. `verifiedLive: false` means inspection
does not contact the provider or prove that a token is still valid. Unknown scope
metadata is different from a known empty scope set. Custom bot credentials may
have no separately stored public identity metadata; the diagnostic marks that
unknown instead of decrypting their secret payload or guessing from a display name.

Slack access depends on the selected user's or bot's grants and conversation
membership. A credential that can list some channels may lack access to another
private channel or its files. Follow the diagnostic notes and the actual provider
error for that credential.

## Download stored tool files

`slack_download` returns a stored file descriptor (`id`, `key`, `context`, `name`,
`type`, `size`, `url`), not inline base64. The URL requires authorization.

For a personal output returned by a direct tool call (`context: copilot`):

```sh
sim tools files download "$FILE_ID" -o ./attachment.pdf
```

For a workflow execution output, use the workflow/run that produced it:

```sh
sim workflows runs files download "$WORKFLOW_ID" "$RUN_ID" "$FILE_ID" -o ./attachment.pdf
```

The downloader uses the configured Sim credential and streams to disk through
the existing safe file writer. Direct personal outputs require their original
human owner and current workspace access; workflow outputs use the run's access
checks. A descriptor's URL or storage key alone grants no access. Execution and
personal output files can expire; copy durable artifacts into workspace files.

## Use editable state for in-place edits

Start a diagnostic read with a compact view:

```sh
sim --output json workflows inspect "$WORKFLOW_ID"
sim --output json workflows inspect "$WORKFLOW_ID" --block-id "$BLOCK_ID" --include-code
```

Inspection returns canonical block IDs, names, enabled states, parent IDs,
connections, and bounded nonempty inputs. It omits credential fields, opaque
credential-bearing values, UI metadata, output schemas, and code by default.
`omittedInputs` identifies withheld fields, and `truncated` identifies inputs
that exceed the diagnostic budget. Automatic redaction cannot recognize every
secret embedded in arbitrary text or code. This view is for inspection, not saving.

`workflows export` produces a sanitized portable representation. Its credential
bindings are cleared; optional reference metadata supports mapped imports into
another workspace. Use [workflow import and sync](/cli/workflow-sync) for that flow.

For an existing workflow, start from `workflows state get`, preserve block IDs
and credential/table references, and use `state replace --dry-run` before saving.
Inspect the validation check coverage, skipped checks, warnings, and removed
bindings. A clean static check cannot verify provider access, model output, or
runtime behavior. Never replace editable state with a portable export merely
because both are JSON.

A semantic edit with `dryRun=true` returns provisional `previewBlockIds` and an
empty `mintedBlockIds`. Commit the edit and use that response's `mintedBlockIds`;
preview IDs are not reserved. Inspect the saved workflow to confirm its enabled
blocks and connections before executing.

## Discover workflows across workspaces

Use `workspaces list`, then `workflows list --workspace <id>` for each relevant
workspace. Follow each list's `nextCursor`; a page is not the entire account.
Workflow results already include the workspace ID, description, folder path,
deployment state, and web URL. `--search` matches workflow names;
`--folder-path` and `--deployed-only` narrow that workspace's results.

There is no account-wide workflow-content search. Narrow using metadata before
inspecting candidate workflows; do not fetch every full draft to discover a
Slack destination or integration. Inspection does not index or search secrets.

## Execute Functions and reference secrets

Read `tools get function_execute` before a direct Function call. JavaScript
references a selected secret with `{{SECRET_NAME}}`, not `process.env`:

```javascript
const token = {{SECRET_NAME}}
return { configured: typeof token === 'string' && token.length > 0 }
```

Use the tool's documented secret-selection parameters and avoid returning the
secret itself. Direct execution uses the authenticated caller's current workspace
permissions; it does not require creating a temporary workflow or supplying an
executor origin.

## Inspect execution and application results separately

```sh
sim --output json logs get "$RUN_ID" --summary
sim --output json workflows runs get "$RUN_ID" --workflow "$WORKFLOW_ID" \
  --select-output "Verify delivery.result"
```

`--summary` reports execution status, recorded failures (including handled
errors), compact failing inputs/outputs, observed block statuses, and file
metadata. It caps trace traversal and field/text output and reports `truncated`
when it omits detail. Binary fields and data URLs are omitted. This is a local
projection of the authorized log response; it reduces terminal/context output,
not the size of the server's log read. Use `logs get --trace` or explicit output
selectors when more detail is needed.

Selectors accept an unambiguous block name or ID followed by an optional output
path. Names are resolved against the **current saved workflow**, ignoring case,
spaces, and dots. Use block IDs for renamed or deleted historical blocks.
Ambiguous names are rejected with candidate IDs. Missing output paths can be
omitted; that does not establish that a block ran successfully.

A completed run can have sent a failure explanation rather than delivered a
document. Have the workflow deliberately emit an `applicationOutcome` field in
its final output, for example:

```json
{
  "applicationOutcome": {
    "status": "verification_blocked",
    "threadId": "<provider-thread-id>",
    "fileIds": []
  }
}
```

Choose application statuses that describe the workflow's result, such as
`delivered`, `clarification_requested`, or `verification_blocked`. The summary
copies this field at the top level, or inside a Function block's `result` or a
Response block's `data` wrapper; it does not infer it from a successful execution or a Slack
message. A null outcome means the workflow did not report one. Trace entries
describe observed work, and cannot prove unrecorded downstream effects or content
quality. Expired trace data may leave no block-level evidence.

## Track long manual runs

Preview a partial retry before repeating external actions:

```sh
sim --output json workflows runs preview "$WORKFLOW_ID" \
  --from-block "$BLOCK_ID" --source-run "$SOURCE_RUN_ID"
```

Check `validation`, `rerunBlocks`, and `upstreamBlocks`. The preview shares the
executor's graph analysis and returns cached-output availability without exposing
output values. It executes no blocks and reserves no run ID. The listed rerun
blocks are candidates, not a promise of execution order: conditions, disabled
blocks, loops, and runtime failures still affect the path. A later run uses the
draft saved at that time; preview does not lock a snapshot.

```sh
sim workflows run "$WORKFLOW_ID" --from-block "$BLOCK_ID" \
  --source-run "$SOURCE_RUN_ID" --follow
```

Manual execution uses the current saved workflow, while an ordinary run uses
the active deployment. The CLI prints a run ID to stderr before sending a manual
request, including partial retries. From another terminal:

```sh
sim workflows runs get "$RUN_ID" --workflow "$WORKFLOW_ID"
sim workflows runs wait "$RUN_ID" --workflow "$WORKFLOW_ID"
```

Status becomes available after the server admits and records the run. A request
rejected before admission may never have a run record. The run ID is a one-shot
identifier, not a replayable idempotency key. After an uncertain network failure,
inspect that same ID before considering another execution; a fresh ID can repeat
external actions.

| Mode | Supported |
| --- | --- |
| Deployed run | Synchronous, `--follow`, or `--async` |
| Manual draft run | Synchronous or `--follow` |
| Manual `--from-block` with `--source-run` | Synchronous or `--follow` |
| `--follow` with `--async` | No |
| Manual execution with `--async` | No; use the printed ID to inspect the active request |

## Inspect an intermediate execution result

Use the existing output selectors with the executor's stop-after control:

```sh
sim --output json workflows run "$WORKFLOW_ID" --stop-after "$FORMATTER_BLOCK_ID" \
  --select-output "$FORMATTER_BLOCK_ID.result"
```

This executes real blocks. It stops scheduling after the target finishes;
already-running parallel branches can still perform actions. It is not a dry
run or a side-effect suppression mode. The control applies to this request and
does not disable blocks or edit the saved graph. It is unavailable with `--async`.
If a condition skips the target, the remaining path can complete normally.
If the run pauses, a later explicit resume does not inherit the stop-after limit.

Deployed execution uses the deployment snapshot. A workflow with only one
runnable Schedule trigger can run directly. When multiple entry points are
ambiguous, select the intended deployed trigger with the API's
`run: { "source": "deployment", "entry": { "type": "trigger", "blockId": "<block-id>" } }`.
Manual trigger execution remains a separate choice that uses the saved draft.

## Preview a Slack message and paginate Stripe results

For Block Kit messages without file attachments, supply meaningful top-level `text` as the fallback for
notifications and accessibility, alongside `blocks`. To check the actual visual
layout, open Slack's [Block Kit Builder](https://app.slack.com/block-kit-builder)
and paste the message payload into its editor. Review the rendered layout and
fallback text separately. Viewing the preview does not post the message; the
builder's **Send to Slack** action does. Slack may require sign-in.
Slack's file-upload completion endpoint treats a block comment and an initial
text comment differently; Sim preserves blocks when both are supplied with files.

Stripe subscription listing uses `starting_after` or `ending_before` with a
subscription ID; do not send both. Check `has_more` before requesting another
page. Subscription search uses a different provider cursor: pass `next_page`
back as `page`, retaining the same search query. The tools expose these response
fields under `metadata`. Use the exact parameter names
published by `tools get stripe_list_subscriptions` and
`tools get stripe_search_subscriptions`.

## Keep generated files organized

Create explicit folders for durable generated artifacts and temporary scratch
work, and pass the destination to file-producing operations that support it.
For example, use a reusable `/Generated/Archives` folder for archives and a
separate `/Scratch` folder for temporary inputs. These are ordinary workspace
folders, with the same permissions and retention as other files; naming one
`Scratch` does not make it automatically expire.

File compression accepts `folderPath` and `onConflict`. `rename` chooses an
available name; `error` refuses a collision. Inspect the returned `path` for the
actual stored location. Omitting the destination retains the existing root
behavior. There is no implicit workspace-wide generated-file destination.
