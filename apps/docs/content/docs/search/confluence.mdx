title: Confluence
description: Search Confluence Cloud with member access and optional service-source restrictions
---

Confluence supports **Member accounts** and **Service account**. Each reader connects their own Confluence account in both modes. Search queries Confluence Cloud directly; Server and Data Center are not supported by this adapter.

## Member accounts

1. An admin adds **Confluence** under **Settings → Sources** and selects **Member accounts**.
2. Each teammate opens **Integrations → Confluence → Connect** and authorizes the appropriate Atlassian account.
3. Search content that account can access. Member mode has no admin space or label configuration.

The default search includes pages and blog posts. The assistant can use CQL to narrow the content type or target a space. Site selection and permissions come from the connected account.

## Set up a central source

1. Add Confluence in Sources, choose **Service account**, and use **Add connection**, or select an existing connection.
2. In **Connect Confluence site**, choose or add the service credential, enter its site, and select **Spaces**. The picker and manual space-key input set the same boundary. **All** includes spaces currently accessible to the service account.
3. Choose the content type and optional label filter, then save the connection. Choose that connection as the integration's service source.
4. Each reader connects their personal Confluence account under **Integrations**.

The source can select pages, blog posts, or both. Multiple labels are alternatives: matching any selected label satisfies that filter. A missing required space selection does not broaden access.

## Using a service account

Use an Atlassian service account with access to the configured site, spaces, and restricted content. Admin status does not bypass page restrictions. Create a scoped API token in **Atlassian Administration → Directory → Service accounts**.

The shared service credential and connector validation use these read scopes:

```text
read:confluence-content.all
read:page:confluence
read:blogpost:confluence
read:attachment:confluence
read:space:confluence
read:label:confluence
search:confluence
read:confluence-space.summary
read:content.metadata:confluence
read:space.permission:confluence
read:confluence-user
read:user:confluence
read:group:confluence
```

In the source form, select **Service account → Add service account**, paste the token, and supply the matching site hostname. This is separate from the shared OAuth app that members authorize. See [Atlassian's service account token instructions](https://support.atlassian.com/user-management/docs/manage-api-tokens-for-service-accounts/).

## How filtering works

Search sends the member's query through their OAuth grant. In service mode, it incorporates the source's content type, space, and label restrictions where supported. Before returning a candidate, Sim uses the source credential to confirm its site, current status, space, type, labels, and readability. The member must also be able to read it.

Reading the document uses the member's connection and repeats the service-boundary checks. Sim does not build a background mirror of Confluence groups or page ACLs for this live path. It returns the page or blog-post content exposed by the current API; it does not perform the old attachment ingestion and OCR pipeline.

Search visits up to four accessible Atlassian sites by default. Native CQL can target a specific cloud site ID and follow its continuation cursor. Confluence's own search freshness and limits still apply.

## Troubleshooting

| Problem | What to check |
| --- | --- |
| Spaces picker is empty | Check the service credential's site, space access, and scopes. Manual space keys remain available. |
| Service account fails validation | Check expiry, site, Confluence app access, and the credential's required read scopes. |
| Member sees no results | Connect their personal account; confirm both that account and the selected service credential can open the content. |
| Blog posts or a labeled page are absent | Check content type, labels, selected spaces, and Confluence's own search results. |
| Results disappear after changing a source | Verify the new boundary and credential; access is checked again on every search and read. |

## Self-hosted operator setup

Configure one shared Confluence OAuth app for teammates' connections:

1. In the [Atlassian developer console](https://developer.atlassian.com/console/myapps/), select or create the deployment's **OAuth 2.0 integration**.
2. Under **Authorization → OAuth 2.0 (3LO)**, add `https://<your-sim-domain>/api/auth/oauth2/callback/confluence` as a callback.
3. Under **Permissions**, add the Confluence API and its full `confluence` scope list from [Sim's OAuth configuration](https://github.com/simstudioai/sim/blob/staging/apps/sim/lib/oauth/oauth.ts), including `read:group:confluence`. Add **User Identity API → read:me**. Sim requests `offline_access` for refresh tokens; the service-account list above does not replace this shared OAuth scope set.
4. Enable sharing under **Distribution**. Set `CONFLUENCE_CLIENT_ID` and `CONFLUENCE_CLIENT_SECRET` from the app's **Settings**, verify `NEXT_PUBLIC_APP_URL`, and restart Sim.
5. Connect from **Integrations** and select the configured site. After changing the OAuth client or requested scopes, update the organization’s provider configuration and have affected teammates reconnect.

The callback must match Sim's scheme, hostname, port, and path exactly. If only the app owner can connect, check **Distribution**. See the [Atlassian OAuth guide](https://developer.atlassian.com/cloud/confluence/oauth-2-3lo-apps/) and [Sim deployment reference](/platform/self-hosting/integrations-oauth).
