title: Gmail
description: Search your connected mailbox with optional service-account label and date restrictions
---

Gmail supports **Member accounts** and **Service account**. Each person connects Gmail in Integrations in either mode. Search reads matching messages from that connected mailbox through the Gmail API; connecting an account does not start indexing.

## Member accounts

An admin adds **Gmail** under **Settings → Sources**, chooses **Member accounts**, and saves. Members then select **Integrations → Gmail → Connect**. Member mode has no admin label, date, category, or mailbox filters. Gmail search syntax and the connected account determine matches.

Search reads email; it does not send or modify messages. The personal account connection is shared with workflow capabilities, so its authorization can include broader scopes.

## Set up a central service account

1. In Google Cloud, enable **Gmail API** and **Admin SDK API**, create a service account, and download its JSON key.
2. In Google Workspace Admin, authorize domain-wide delegation for that service account's numeric client ID with these scopes:

```text
https://www.googleapis.com/auth/gmail.readonly
https://www.googleapis.com/auth/admin.directory.user.readonly
```

3. In **Settings → Sources → Gmail**, choose **Service account** and **Add connection**. Add or select the Google service credential.
4. Set **Delegated administrator** to an active Workspace administrator who can read Directory users. Set any selected **Users**, labels, date range, exclusions, and search filter, then save.
5. Select the saved connection as Gmail's service source. Every reader still connects their personal Gmail account in Integrations.

Use primary Workspace email addresses for selected users. Leaving **Users** empty permits eligible connected mailboxes in the same Workspace customer; it does not search everyone else's mailbox. Gmail delegation always targets the connected member's verified provider identity.

For a shared key, see [one service account for all three Google sources](/search/google-drive#one-service-account-for-drive-gmail-and-calendar).

## Service-source settings

| Setting | Effect |
| --- | --- |
| Users | Optional allowed primary Workspace mailboxes. A member outside the selection gets no matches through this source. |
| Labels | Selected labels are alternatives. The picker browses the delegated administrator's mailbox and saves label names, since custom label IDs differ by mailbox. |
| Date Range | A rolling window checked against each message. |
| Search Filter | A Gmail query that matching messages must also satisfy. |
| Exclude Promotions / Social | Additional category exclusions; the existing service-source defaults exclude both. |

These settings apply only to service mode. They do not appear as member-account configuration.

## How INBOX filtering works

For **Labels = INBOX**, a connected member's search follows these steps:

1. Sim verifies the connected Gmail identity and the source's active Workspace user/customer match.
2. Gmail searches that member's mailbox with their query, the INBOX restriction, and the configured category exclusions.
3. Sim uses the service account delegated to that same mailbox to fetch each candidate's current metadata.
4. It checks current label IDs, the source's rolling date range, and any custom query. Custom labels are resolved within that member's mailbox. Custom queries are verified against the exact candidate message.
5. Only allowed messages are returned. Reading a result fetches that individual message through the member's connection and repeats the source checks.

A message the member can read but that is outside INBOX does not pass. Search does not substitute the administrator's mailbox or expose another message from the same thread merely because one message matched.

Gmail API matching is message-based and differs from Gmail's UI for some thread-wide and alias searches. See [Google's filtering guide](https://developers.google.com/workspace/gmail/api/guides/filtering). Attachment search operators can select a message; Search does not separately ingest attachment contents.

## Troubleshooting

| Problem | Next step |
| --- | --- |
| Google rejects delegation | Check the numeric client ID, delegated scopes, pending Workspace approval, and JSON key. |
| Directory user is unavailable | Use an active primary Workspace user in the source's customer and an administrator with user-read access. |
| Connected member sees no results | Check their mailbox, selected Users, labels, date range, exclusions, and custom query. |
| Custom label is missing | Confirm that label exists in the member's mailbox; administrator and member label IDs need not match. |
| Provider is rate limited or coverage is incomplete | Retry as directed or narrow the query; there is no document-indexing retry. |

## Self-hosted operator setup

Configure the deployment’s Google OAuth client for every member’s personal connection, including members using a service-account source. This is separate from domain-wide delegation.

1. In [Google Cloud Console](https://console.cloud.google.com/), select your project. Open **APIs & Services → Library**, find **Gmail API**, and enable it.
2. Open **Google Auth platform → Branding**. Select **Get started** if needed, then enter the app name, support email, and contact email. Under **Audience**, use **Internal** only for an app limited to your Google Workspace organization; otherwise use **External** and add test users while testing. Review the app's permissions under **Data Access → Add or remove scopes**, using the current Sim scopes below. Follow Google's [consent and verification guidance](https://developers.google.com/workspace/guides/configure-oauth-consent) for your audience.
3. Open **Google Auth platform → Clients → Create client**. Choose **Web application**, give the client a name, and add the URI below under **Authorized redirect URIs**. If this instance already has a Google client, add this URI to that client instead. See [Google's credential setup](https://developers.google.com/workspace/guides/create-credentials#web-application).
4. Save the client ID and secret as `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET`. Set `NEXT_PUBLIC_APP_URL` to the same Sim origin used in the callback, then restart Sim. See [Integrations & OAuth](/platform/self-hosting/integrations-oauth). If you change an existing deployment's OAuth client or scopes, an organization admin updates the provider configuration and affected teammates reconnect.

```text
https://<your-sim-domain>/api/auth/oauth2/callback/google-email
```

One OAuth client can register callbacks for all three Google services. Use your exact Sim origin and add only the callbacks for services you enable.

The member-account OAuth connection uses these scopes:

```text
openid
https://www.googleapis.com/auth/userinfo.email
https://www.googleapis.com/auth/userinfo.profile
https://www.googleapis.com/auth/gmail.modify
https://www.googleapis.com/auth/gmail.send
https://www.googleapis.com/auth/gmail.labels
```

The personal OAuth connection also supports workflow actions, so its declared scopes can be broader than Search’s read-only requests. The service credential uses the separate delegation scopes above.
