Google service accounts can access shared resources directly or impersonate a Google Workspace user through domain-wide delegation. This guide covers the JSON key, required APIs, delegation scopes, and credential setup in Sim.

For example, you could build a workflow that iterates through a list of employees, impersonates each one to read their Google Docs, and uploads the contents to a shared knowledge base — all without requiring any of those users to sign in.

For Google Cloud APIs such as BigQuery and Vertex AI, and for Gmail, Drive, Docs, Sheets, and Calendar through domain-wide delegation, you can skip the JSON key entirely: see [Keyless Google Cloud access](#keyless-google-cloud-access) and [Keyless domain-wide delegation](#keyless-domain-wide-delegation).

## Prerequisites

Create the service account and enable its APIs in Google Cloud. Configure the Google Workspace Admin Console only when using domain-wide delegation.

### 2. Enable the required APIs [#2-enable-the-required-apis]

In the Google Cloud Console, go to **APIs & Services** → **Library** and enable the APIs for the services your workflows will use. See the [scopes reference](#scopes-reference) below for the full list of APIs by service.

### 3. Set up domain-wide delegation [#3-set-up-domain-wide-delegation]

<Steps>
  <Step>
    In the Google Cloud Console, go to **IAM & Admin** → **Service Accounts**, click on your service account, and copy the **Client ID** (the numeric ID, not the email)
  </Step>
  <Step>
    Open the [Google Workspace Admin Console](https://admin.google.com/) and navigate to **Security** → **Access and data control** → **API controls**
  </Step>
  <Step>
    Click **Manage Domain Wide Delegation**, then click **Add new**
  </Step>
  <Step>
    Paste the **Client ID** from your service account, then add the OAuth scopes for the services your workflows need. Copy the full scope URLs from the [scopes reference](#scopes-reference) below — only authorize scopes for services you plan to use.

    <div className="flex justify-center">
      <Image
        src="/static/credentials/gcp-add-client-id.png"
        alt="Google Workspace Admin Console — Add a new client ID with OAuth scopes"
        width={948}
        height={846}
        className="my-4"
      />
    </div>
  </Step>
  <Step>
    Click **Authorize**
  </Step>
</Steps>

Domain-wide delegation requires a Google Workspace **super administrator**. Send that administrator the Client ID and required scopes. Changes can take up to 24 hours to propagate.

## Add the service account to Sim [#adding-the-service-account-to-sim]

Once Google Cloud and Workspace are configured, add the service account as a credential in Sim.

<Steps>
  <Step>
    Open **Integrations** from your workspace sidebar
  </Step>
  <Step>
    Search for "Google Drive" and open it, or use another Google integration that supports service-account credentials. Click **Add to Sim** and choose **Add service account**
  </Step>
  <Step>
    Paste the full contents into **JSON key**, or use **Or upload a file** to select the JSON key file.
    </Step>
  <Step>
    Give the credential a display name (the service account email is used by default)
  </Step>
  <Step>
    Click **Add service account**
  </Step>
</Steps>

The JSON key file is validated for the required fields (`type`, `client_email`, `private_key`, `project_id`) and encrypted before being stored.

## Use delegated access in workflows [#using-delegated-access-in-workflows]

When you use a Google block (Gmail, Sheets, Drive, etc.) in a workflow and select a service account credential, an **Impersonated Account** field appears below the credential selector.

Enter the email address of the Google Workspace user you want the service account to act as. For example, if you enter `alice@yourcompany.com`, the workflow will send emails from Alice's account, read her spreadsheets, or access her calendar — depending on the scopes you authorized.

<Callout type="warn">
The impersonated email must belong to a user in the Google Workspace domain where you configured domain-wide delegation. Impersonating external email addresses will fail.
</Callout>

## Shared access and key rotation

Leave **Impersonated Account** blank to authenticate as the service account itself. Share supported resources, such as a Sheet, with its service-account email. This does not grant access to a user’s Gmail. A Google Cloud IAM role alone does not grant access to Google Workspace files or mailbox data.

Domain-wide delegation requires a Google Workspace super administrator. It authorizes impersonation within that Workspace domain, subject to the authorized scopes and the impersonated user’s access. Consumer Gmail accounts and users outside that domain cannot be impersonated. Access also depends on the license required by the target service. See [Google’s service-account authorization guide](https://developers.google.com/identity/protocols/oauth2/service-account).

**Google Ads** never uses domain-wide delegation: add the service account's email as a user in the Google Ads account (**Admin > Access and security**); it signs in as itself. Enable the Google Ads API in the project that owns the service account; that project's Google Ads API access level applies. See [Google Ads](/integrations/google_ads).

A credential can serve multiple supported Google services when their APIs and scopes are configured. To rotate its key, create a replacement JSON key, update the credential in Sim, verify access, then delete the old key in Google Cloud.

## Keyless Google Cloud access [#keyless-google-cloud-access]

A Google service account credential can also be **keyless**: Sim stores no key. Instead, your Google Cloud project trusts Sim through [Workload Identity Federation](https://cloud.google.com/iam/docs/workload-identity-federation-with-other-providers). On each run, Sim signs a short-lived token for this credential's own subject, exchanges it at Google's Security Token Service for a federated token, and uses that to impersonate your service account. The service account's IAM roles decide what workflows can do, exactly as with a JSON key.

<Callout type="info">
Keyless credentials work with Google Cloud APIs that the service account calls as itself: **BigQuery**, and **Vertex AI** in every block that runs a Vertex model (pick the credential in its **Google Cloud Account** field). With [keyless domain-wide delegation](#keyless-domain-wide-delegation) they also work with **Gmail**, **Google Drive**, **Google Docs**, **Google Sheets**, and **Google Calendar**, acting as one Workspace user. Other Google Workspace blocks need a JSON key.
</Callout>

<Steps>
  <Step>
    In the [Google Cloud Console](https://console.cloud.google.com/), enable the IAM, Resource Manager, Service Account Credentials, and Security Token Service APIs in the project that will hold the workload identity pool, and note its **project number** (on the project's Dashboard; it's numeric, not the project ID).
  </Step>
  <Step>
    Create or pick a service account, and grant it the roles your workflows need (for example, BigQuery Data Viewer and BigQuery Job User, or Vertex AI User). No key is needed.
  </Step>
  <Step>
    In Sim, open the **Google BigQuery** integration, choose **Add service account**, and set **Authentication** to **Workload Identity Federation (keyless, via Sim OIDC)**. Enter the project number, a pool ID and provider ID (4 to 32 lowercase letters, digits, or hyphens, not starting with `gcp-`), and the service account email (`name@project-id.iam.gserviceaccount.com`; user-managed service account only, so default accounts such as `…@developer.gserviceaccount.com` are refused).
  </Step>
  <Step>
    The dialog shows the **Issuer**, **Audience**, and **Subject**, and three `gcloud` commands with your values filled in. Run them in that project. They run against the project number you entered and create the pool, an OIDC provider for Sim's issuer with the attribute mapping `google.subject=assertion.sub` and an attribute condition that accepts only this credential's subject, and grant that subject `roles/iam.workloadIdentityUser` on the service account. If the pool already exists, skip the first command:

    ```bash
    gcloud iam workload-identity-pools create POOL_ID \
        --project="PROJECT_NUMBER" \
        --location="global" \
        --display-name="Sim"

    gcloud iam workload-identity-pools providers create-oidc PROVIDER_ID \
        --project="PROJECT_NUMBER" \
        --location="global" \
        --workload-identity-pool="POOL_ID" \
        --issuer-uri="ISSUER" \
        --attribute-mapping="google.subject=assertion.sub" \
        --attribute-condition="assertion.sub=='SUBJECT'"

    gcloud iam service-accounts add-iam-policy-binding SERVICE_ACCOUNT_EMAIL \
        --project="PROJECT_NUMBER" \
        --role="roles/iam.workloadIdentityUser" \
        --member="principal://iam.googleapis.com/projects/PROJECT_NUMBER/locations/global/workloadIdentityPools/POOL_ID/subject/SUBJECT"
    ```

    By default the provider sets no allowed audiences, so it accepts its own resource name, which Sim's token carries as its `aud`.
  </Step>
  <Step>
    Save in Sim. Sim exchanges a token at STS and impersonates the service account; a token from that step proves the setup works. It also checks that a subject no credential holds can't impersonate the service account, so only this credential can use it. New IAM bindings can take a few minutes to apply; if saving fails right after you run the commands, wait and try again.
  </Step>
</Steps>

<Callout type="warn">
Keep the attribute condition and bind the role to the exact `principal://…/subject/SUBJECT` member. Without the condition, the provider accepts a token for any Sim subject, and a role granted to a `principalSet` for the whole pool would let other Sim credentials act with it. Sim refuses to save a service account that another subject can impersonate, but it can't see roles you grant the pool directly on other resources.
</Callout>

### Custom audience [#keyless-custom-audience]

To pin the provider to a value of your own instead of its resource name, enter it under **Audience** (up to 255 letters, digits, and `. _ ~ : / ? # @ & + = % -`). Sim's token then carries that value as its `aud`, and the setup commands add it to the provider's [allowed audiences](https://cloud.google.com/iam/docs/reference/rest/v1/projects.locations.workloadIdentityPools.providers#oidc), which then accept only the listed values:

```bash
gcloud iam workload-identity-pools providers create-oidc PROVIDER_ID \
    ... \
    --allowed-audiences="AUDIENCE"
```

For an existing provider, run `gcloud iam workload-identity-pools providers update-oidc PROVIDER_ID --project="PROJECT_NUMBER" --location="global" --workload-identity-pool="POOL_ID" --allowed-audiences="AUDIENCE"` before reconnecting the credential with the new audience. Sim still exchanges the token at STS for the provider itself. To go back to the default, clear **Audience** and remove the allowed audiences from the provider (or add its resource name, `https://iam.googleapis.com/projects/PROJECT_NUMBER/locations/global/workloadIdentityPools/POOL_ID/providers/PROVIDER_ID`). Another cloud's default audience, such as `sts.amazonaws.com`, is refused.

Each keyless credential has its own subject; reconnecting keeps it by default so your provider and binding keep working. Use one provider per credential (a pool can hold many). Keyless credentials are available for workspace credentials, not organization credentials. Sim uses impersonation rather than direct federated access because some Google Cloud APIs don't accept federated tokens, and impersonation keeps the same identity a JSON key would use.

Self-hosted deployments need `WORKLOAD_IDENTITY_SIGNING_KEY` set and an `https` issuer Google can reach over the public internet. See [AWS credentials](/integrations/aws-credentials#self-hosted-deployments).

### From the API or CLI [#keyless-api-cli]

Run `sim credentials keyless-subject google-service-account`, trust the printed subject as above, then add `projectNumber`, `poolId`, `providerId`, and `serviceAccountEmail` (and optionally `audience`) to its `keylessConfig` and pass it to `sim credentials create google-service-account`. See [the CLI credentials reference](/cli/credentials) for the full two-step example; the proof expires after 24 hours and works only for the user who requested it. For domain-wide delegation, also add `"delegation": {"user": "alice@yourcompany.com", "services": ["gmail", "google-drive"]}`, listing any of `gmail`, `google-drive`, `google-docs`, `google-sheets`, and `google-calendar`.

### Keyless domain-wide delegation [#keyless-domain-wide-delegation]

A keyless credential can also act as one Google Workspace user in Gmail, Google Drive, Google Docs, Google Sheets, and Google Calendar, without a JSON key. Google's [domain-wide delegation guidance](https://knowledge.workspace.google.com/admin/apps/domain-wide-delegation-best-practices) recommends this: on each run, Sim exchanges its token at STS as above, then asks the IAM Service Account Credentials API to [sign](https://cloud.google.com/iam/docs/reference/credentials/rest/v1/projects.serviceAccounts/signJwt) the same delegation assertion a JSON key would sign, with your user as its subject, and exchanges it at Google's OAuth token endpoint.

<Steps>
  <Step>
    Set up the keyless credential as above, from the Gmail, Google Drive, Google Docs, Google Sheets, or Google Calendar integration. Under **Domain-wide delegation**, choose the services the credential may use, and enter the **Workspace user** it acts as.
  </Step>
  <Step>
    Grant the subject `roles/iam.serviceAccountTokenCreator` on the service account instead of `roles/iam.workloadIdentityUser`; the setup commands do this when delegation is on. Signing needs the `iam.serviceAccounts.signJwt` permission, which Service Account Token Creator includes and Workload Identity User does not. Token Creator also grants permissions Sim doesn't use, such as `iam.serviceAccounts.signBlob`; for least privilege, grant a [custom role](https://cloud.google.com/iam/docs/creating-custom-roles) with just `iam.serviceAccounts.signJwt` and `iam.serviceAccounts.getAccessToken` (the second keeps BigQuery and Vertex AI working with the same credential).
  </Step>
  <Step>
    In the Google Cloud console, enable each service's API (see the [scopes reference](#scopes-reference)) in the project that owns the service account, and copy the service account's numeric **Unique ID** (its OAuth 2 client ID).
  </Step>
  <Step>
    Have a Google Workspace super administrator authorize that client ID in the Admin console under **Security** → **Access and data control** → **API controls** → **Manage Domain Wide Delegation**, for the scopes the dialog lists under **Scopes to authorize**.
  </Step>
  <Step>
    Save in Sim. For each service, Sim signs in as the Workspace user and makes one read (the Gmail profile, Drive's account details, or the first calendar in the calendar list), so a missing role or authorization, or a disabled Gmail, Drive, or Calendar API, shows up now rather than in a run. Google Docs and Google Sheets use Drive's scopes and are checked through the Drive API only: enable the Google Docs API and Google Sheets API yourself, since a disabled one shows up only in a run.
  </Step>
</Steps>

<Callout type="warn">
A keyless credential acts only as the Workspace user you entered. A workflow that sets a different **Impersonated Account** is refused; create one credential per user. To add a service or change the user, reconnect the credential and authorize any new scopes first; reconnecting opens on the credential's current user and services.
</Callout>

### Troubleshooting keyless access

- **"Google Cloud refused Sim's token for this workload identity provider":** the project number, pool ID, or provider ID doesn't match; the provider is disabled or uses a different issuer; its allowed audiences don't accept the credential's audience (with the default, it needs none set, or its own resource name among them; with a custom audience, that value must be listed); or its attribute condition doesn't allow this credential's subject.
- **"Google Cloud could not fetch the signing keys from Sim's issuer":** the issuer isn't reachable over public HTTPS (self-hosted deployments).
- **"The service account … does not let this credential impersonate it":** run the `add-iam-policy-binding` command with the exact member shown, and enable the IAM Service Account Credentials API.
- **"This service account also trusts other Sim credentials":** remove any `principalSet` binding for the pool from the service account and keep the attribute condition.
- **"… does not let this credential sign for it, which domain-wide delegation needs":** grant `roles/iam.serviceAccountTokenCreator` on the service account to the exact `principal://…/subject/SUBJECT` member, and enable the IAM Service Account Credentials API.
- **"Google Workspace has not authorized this service account's domain-wide delegation":** authorize the service account's client ID for every scope the dialog lists in the Admin console. New authorizations can take a while to apply.
- **"Your Google Workspace admin policies block one or more of these scopes":** a Workspace administrator must allow the service account's client ID under **API controls**, third-party app access.
- **"Google reports the service account … is disabled" (or "was deleted"):** enable the service account in Google Cloud under **IAM & Admin > Service Accounts**, or restore a deleted one within 30 days.
- **"Google refused to sign in as …":** the address isn't an active user in your Workspace domain.
- **"… but the Gmail API refused the request" (or Drive, Calendar):** enable that API in the project that owns the service account, and check the user has the service.
- **A block fails with "This credential cannot be used here":** the block needs scopes the credential's delegation doesn't authorize (or it isn't BigQuery or Vertex AI), or it sets an **Impersonated Account** other than the credential's Workspace user. Reconnect the credential with that block's service, or use a JSON key.

A keyless credential is used only for the scopes listed under **Scopes to authorize**, and Sim refuses anything else before contacting Google. Like Google, Sim authorizes by scope, not by block: Drive, Docs, and Sheets share those scopes, so a credential delegated for any of them also serves the other two and their file pickers, which ask for read-only Drive access that the authorized `drive` scope covers. Read-only Gmail access, which the Gmail label picker and knowledge base connector ask for, is served with the authorized `gmail.modify` scope, and the Google Calendar knowledge base connector's read-only events access with the authorized `calendar` scope. Knowledge base connectors that need other scopes, such as the admin directory scopes, need a JSON key.
