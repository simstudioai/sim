A Microsoft app credential signs in as a Microsoft Entra app registration instead of a person (the OAuth 2.0 client credentials flow). One credential works for the **Azure AD** (Microsoft Entra ID), **SharePoint**, **Microsoft Intune**, **Power BI**, **Azure Data Explorer**, **Microsoft Dataverse**, and **Dynamics 365** blocks. Connecting a Microsoft account through OAuth keeps working exactly as before; the app credential is an additional option in the same account picker.

<Callout type="info">
Outlook, OneDrive, Excel, Word, Planner, and Teams act on behalf of a signed-in person and don't accept an app credential. The Azure AD **Reset password** operation also needs a signed-in admin, because Microsoft Graph doesn't support application permissions for it.
</Callout>

## Choose how the app signs in

| Option | What Sim stores | When to use it |
| --- | --- | --- |
| **Federated credential (keyless, via Sim OIDC)** | Nothing secret: the tenant ID, client ID, and this credential's subject | Recommended. No secret to rotate, expire, or leak. |
| **Client secret** | The tenant ID, client ID, and client secret | Quick setup. Secrets expire, so plan to rotate them. |
| **Certificate** | The tenant ID, client ID, the certificate, and its private key | When your organization requires certificate credentials. Sim signs each token request with the key. |

Every option resolves on Sim's servers at run time, and tokens never appear in block outputs, logs, or anything a model sees. Azure AD, SharePoint, and Intune blocks get a Microsoft Graph token; Power BI blocks get a Power BI REST API token; Azure Data Explorer blocks get a token for the cluster each block names; Dataverse and Dynamics 365 blocks get a token for the credential's own environment.

## Register the app and grant permissions

<Steps>
  <Step>
    In the [Microsoft Entra admin center](https://entra.microsoft.com), go to **App registrations** → **New registration**. A single-tenant app is fine. Copy the **Application (client) ID** and **Directory (tenant) ID** from its Overview page.
  </Step>
  <Step>
    Under **API permissions** → **Add a permission** → **Microsoft Graph** → **Application permissions**, add what your workflows need, then select **Grant admin consent**. Application permissions always need admin consent. For example:
    - Azure AD: `User.Read.All` or `User.ReadWrite.All`, `Group.ReadWrite.All`, `GroupMember.ReadWrite.All`, `AuditLog.Read.All` for sign-in and audit logs, `Policy.Read.All` for conditional access, `UserAuthenticationMethod.Read.All` for authentication methods, `User.RevokeSessions.All` to revoke sessions. Setting a password needs `User-PasswordProfile.ReadWrite.All` **and** the app assigned at least the User Administrator role.
    - SharePoint: `Sites.Read.All` or `Sites.ReadWrite.All`. Creating and editing pages needs `Sites.ReadWrite.All`. `Sites.Selected` limits the app to sites you grant it, but searching for sites doesn't work with it, so enter site IDs directly.
    - Intune: `DeviceManagementManagedDevices.Read.All` for devices and detected apps, `DeviceManagementConfiguration.Read.All` for compliance policies, their device statuses, and device configurations, and `DeviceManagementManagedDevices.PrivilegedOperations.All` to sync, restart, remotely lock, or retire a device. The tenant needs an active Intune license.
  </Step>
  <Step>
    Power BI doesn't use API permissions either; Microsoft recommends adding none for a Power BI service principal. A Power BI admin turns on **Service principals can use Fabric APIs** (formerly **Allow service principals to use Power BI APIs**) under **Admin portal** → **Tenant settings** → **Developer settings**, for the organization or a security group that contains the app. Then add the app to each workspace the workflows use as a **Member** or **Admin** (**Manage access** on the workspace). A service principal has no **My workspace**, and DAX queries don't run as one against semantic models with row-level security or SSO; **Execute DAX query** also needs the **Dataset Execute Queries REST API** tenant setting.
  </Step>
  <Step>
    Azure Data Explorer doesn't use API permissions. Grant the app a database role on the cluster instead, for example `.add database <DATABASE> viewers ('aadapp=<clientId>;<tenantId>')`.
  </Step>
  <Step>
    Dataverse and Dynamics 365 don't use API permissions. Instead, in the [Power Platform admin center](https://admin.powerplatform.microsoft.com), open the environment → **Settings** → **Users + permissions** → **Application users** → **New app user**, add this app, pick a business unit, and assign a security role. Then enter the environment URL (like `https://contoso.crm.dynamics.com`) on the credential.
  </Step>
</Steps>

## National clouds [#national-clouds]

Choose the **Cloud** the app is registered in: **Global** (which includes Microsoft 365 GCC), **US Government (GCC High)**, **US Government (DoD)**, or **China (operated by 21Vianet)**. Each is a separate Microsoft Entra deployment, and tokens from one cloud don't work in another. Sim signs in at that cloud's endpoint (`login.microsoftonline.com`, `login.microsoftonline.us`, or `login.partner.microsoftonline.cn`) and checks the app against that cloud's Microsoft Graph when you save.

Only **Azure Data Explorer** runs outside the global cloud: a cluster in `kusto.usgovcloudapi.net` takes a US Government credential, and one in `kusto.chinacloudapi.cn` a China credential. The Azure AD, SharePoint, Intune, Power BI, Dataverse, and Dynamics 365 blocks call global-cloud endpoints, so they refuse a national-cloud credential, and a Dataverse environment URL can be saved only on a global credential.

## Set up a keyless federated credential [#keyless-federated-credential]

<Steps>
  <Step>
    In Sim, add a **Microsoft app credential**, choose **Federated credential (keyless, via Sim OIDC)**, and enter the tenant ID and client ID. The dialog shows an **Issuer**, **Audience**, and **Subject**.
  </Step>
  <Step>
    In the app registration, go to **Certificates & secrets** → **Federated credentials** → **Add credential** → **Other issuer**. Paste the **Issuer** and the **Subject identifier** exactly as shown, leave **Audience** at `api://AzureADTokenExchange` (or edit it to your custom audience, below), and give it a name. Matching is case-sensitive.
  </Step>
  <Step>
    Save in Sim. Sim requests a token as the app and reads the app's own service principal from Microsoft Graph, which needs no extra permission. It also checks that the app refuses a subject no credential holds, so only this credential can use the app. A new federated credential can take a few minutes to take effect; if saving fails with a matching error right after you add it, wait and try again.
  </Step>
</Steps>

### Use your own audience [#custom-audience]

By default, Sim's token carries the audience `api://AzureADTokenExchange`, the value Microsoft recommends. To make the federated credential accept only tokens issued for your app, enter your own value in the dialog's **Audience** field (up to 255 letters, digits, and `. _ ~ : / ? # @ & + = % -`, such as `api://contoso-sim`), and set the federated credential's **Audience** to the same value. Entra takes exactly one audience per federated credential and matches it case-sensitively. Sim uses that audience for every token it requests for the credential, including the checks it runs when you save. Another cloud's default audience (such as `sts.amazonaws.com`) is refused.

To change the audience later, edit the federated credential first, then reconnect in Sim with the new value. Clearing the field on reconnect returns to the default.

An app can have up to 20 federated credentials. Each Sim credential has its own subject, and reconnecting keeps the subject by default so the federated credential keeps working. Keyless credentials are available for workspace credentials, not organization credentials.

### From the API or CLI [#keyless-api-cli]

Run `sim credentials keyless-subject microsoft-app-service-account`, trust the printed subject as above, then add `tenantId` and `clientId` (optionally `environmentUrl`, `cloud` as `usgov`, `usgov_dod`, or `china`, and `audience` for a [custom audience](#custom-audience)) to its `keylessConfig` and pass it to `sim credentials create microsoft-app-service-account`. See [the CLI credentials reference](/cli/credentials) for the full two-step example; the proof expires after 24 hours and works only for the user who requested it.

## Use a client secret or certificate

- **Client secret:** under **Certificates & secrets** → **Client secrets** → **New client secret**, copy the secret's **Value** (not the Secret ID).
- **Certificate:** upload the certificate's public part (`.cer`, `.pem`, or `.crt`) under **Certificates & secrets** → **Certificates**, then paste the certificate and its unencrypted PEM RSA private key (2048 to 4096 bits) into Sim. Sim checks the key belongs to the certificate before saving, and signs a PS256 assertion with the certificate's SHA-256 thumbprint.

## Self-hosted deployments

Keyless credentials need `WORKLOAD_IDENTITY_SIGNING_KEY` set and an `https` issuer Microsoft Entra can reach over the public internet. See [AWS credentials](/integrations/aws-credentials#self-hosted-deployments) for the same settings and for rotating the signing key. App credentials sign in at the Microsoft Entra endpoint of the credential's cloud, so the server needs outbound access to it; Dataverse environments are public-cloud only.

## Troubleshooting

- **"No federated credential on this app matches…":** the federated credential's issuer, subject, or audience differs from the dialog (check case and trailing slashes; the error names the audience Sim presented), it's on a different app than the client ID, or it was added moments ago.
- **"Microsoft Entra rejected the client secret":** you pasted the Secret ID, or the secret was deleted. **"This client secret has expired":** create a new one and reconnect.
- **"…could not verify the signed assertion":** the certificate in Sim isn't the one uploaded to the app registration.
- **"…the Dataverse environment did not accept it":** add the app as an application user of the environment with a security role.
- **A block fails with 403 "Insufficient privileges":** the app is missing an application permission for that operation, or admin consent wasn't granted after adding it.
