Data drains periodically export one source of retained Sim data to a destination you control. Organization owners and admins manage configuration and run history because those records expose destination identifiers and URLs. Billing-enabled deployments require Enterprise; billing-disabled deployments use the feature and scheduler configuration under [Self-hosted setup](#self-hosted-setup).

A new drain starts with all retained history. Delivery is at least once: retries, partial acceptance, or a crash after delivery can duplicate rows. Deduplicate downstream by each source row's `id`.

## Create and verify a drain

1. Prepare the destination and credentials. Sim does not create buckets, containers, datasets, or tables.
2. Open **Settings → Organization → Data drains** and click **Create drain**.
3. On **New drain**, enter a name unique within the organization, choose one source, a destination, and **Every hour** or **Every day**.
4. Fill the destination fields below and click **Create**.
5. Open the drain's detail page. Use **Test connection**, then **Run now** and check **Recent runs** and the destination's received rows.

The detail page shows the last ten runs with status, trigger, time, row count, bytes, and failure details. Destination locators are also available through API run reads. **Run now** requires an enabled drain; an overlapping run can be refused. The **Enabled** switch pauses future runs without deleting configuration or the cursor.

## Sources and row format

Create separate drains for different sources. Every delivered row is JSON-safe NDJSON: one JSON object per line, with an `id` for deduplication.

| UI source | Wire value | Records |
| --- | --- | --- |
| Workflow logs | `workflow_logs` | Terminal workflow executions. |
| Job logs | `job_logs` | Terminal background jobs for deployed APIs, schedules, and webhooks. |
| Audit logs | `audit_logs` | Organization and workspace audit events, including departed actors. |
| Chats | `copilot_chats` | Chat snapshots, including organization-owned chats outside a workspace. |
| Chat runs | `copilot_runs` | Terminal Chat runs with correlation context; controller tokens and billing recovery receipts are excluded. |

Workflow, job, and Chat-run cursors use terminal timestamps; audit and Chat cursors use creation time. Reads use the primary database and leave a five-minute stability window. This reduces late-commit gaps but does not guarantee change-data capture.

Chats are point-in-time snapshots. Later changes to messages, title, or `lastSeenAt` are not emitted again. An append-only archive therefore does not track every subsequent change to a conversation.

The export uses each source's row schema. Inspect representative rows before defining warehouse columns; BigQuery receives top-level fields directly. Drains do not apply a new blanket PII scrub. Workflow log masking depends on the stored [data-retention redaction policy](/platform/enterprise/data-retention) used when the data was persisted; configuring `PII_URL` alone does not sanitize exported history.

## Destination reference

### Amazon S3 and compatible stores

Writes one NDJSON object per chunk.

| Field | Requirement |
| --- | --- |
| **Bucket** | Existing bucket. |
| **Region** | AWS region, such as `us-east-1`. |
| **Prefix** | Optional object prefix; trailing slash is optional. |
| **Access key ID / Secret access key** | Credentials with `s3:PutObject`. `s3:DeleteObject` allows cleanup of the zero-byte connection-test probe; without it, the probe can remain. |
| **Endpoint** | Optional HTTPS endpoint for a compatible store; leave blank for AWS. Sim Cloud requires public addresses. Self-hosted Sim can use private MinIO/Ceph or loopback endpoints permitted by its [outbound-network policy](/platform/self-hosting/security#the-ssrf-boundary). |
| **Force path-style** | Enable if the provider requires it. Leave off for standard AWS virtual-hosted addressing. |

Objects use `AES256` server-side encryption and this layout:

```text
{prefix}/{source}/{drainId}/{yyyy}/{mm}/{dd}/{runId}-{seq}.ndjson
```

The final SDK hostname is validated and its resolved address pinned. Signed request paths are preserved without redirects. An outbound gateway that cannot preserve signed targets fails closed.

### Google Cloud Storage

Supply an existing **Bucket**, optional **Prefix**, and the full **Service account JSON key**. The service account needs `storage.objects.create`; `storage.objects.delete` lets the connection test remove its probe. Sim uses OAuth2 service-account JWT authentication and the GCS JSON API.

Object names use the S3 layout above. `sim-*` object metadata uses `x-goog-meta-*` headers.

### Azure Blob Storage

Supply **Account name** (3–24 lowercase characters), an existing **Container**, optional **Prefix**, and an **Account key** with write access. Each chunk becomes an NDJSON block blob using the same object layout. Metadata keys are lowercased for Azure.

**Endpoint suffix** supports `blob.core.usgovcloudapi.net` for US Gov and `blob.core.chinacloudapi.cn` for China. Sim also accepts the legacy Germany suffix `blob.core.cloudapi.de`; verify that the particular account still uses that endpoint before selecting it.

### Google BigQuery

Supply **Project ID**, **Dataset ID**, **Table ID**, and a **Service account JSON key**. Domain-scoped project IDs such as `example.com:my-project` are accepted. The table must already exist with compatible columns for the source's top-level fields; rows are not wrapped in one JSON or STRING column. Sim sets `ignoreUnknownValues: false`.

The account needs `roles/bigquery.dataEditor` for inserts and `roles/bigquery.metadataViewer` for the `tables.get` connection probe. Sim uses OAuth2 service-account JWT authentication and `tabledata.insertAll`.

Each row's `insertId` uses `{drainId}-{runId}-{sequence}-{index}`; IDs exceeding 128 characters are hashed. BigQuery offers best-effort deduplication for repeated IDs for up to one minute, so duplicates remain possible during any retry. Partial `insertErrors` fail the chunk and report row indices; rows already accepted can be repeated. Deduplicate source IDs downstream. See [BigQuery streaming behavior](https://docs.cloud.google.com/bigquery/docs/write-api-rest).

Sim's request guards are **10 MiB and 50,000 rows**. The tighter source-record and chunk limits below normally apply first.

### Snowflake

Supply **Account**, **User**, **Warehouse**, **Database**, **Schema**, **Table**, and an unencrypted PKCS8 RSA **Private key (PEM)**. Prefer `<orgname>-<acctname>`; legacy `<locator>.<region>.<cloud>` identifiers are also accepted. Register the matching public key on the user with `ALTER USER ... SET RSA_PUBLIC_KEY = '...'`.

The user needs `INSERT` on the existing table and `USAGE` on its warehouse, database, and schema. **Role** is optional. **Column** is an existing VARIANT column, defaulting to `DATA`.

Sim uses key-pair JWT authentication and SQL API v2. Each chunk uses `INSERT INTO "DB"."SCHEMA"."TABLE" ("col") SELECT PARSE_JSON(column1) FROM VALUES (?), ...`, with one TEXT binding per row. Identifiers are quoted to preserve case. The runner polls asynchronous `202` responses. Sim guards destination JSON at 16 MiB per row; the source-record limit is the tighter 1 MiB. This is a Sim limit rather than a statement of Snowflake's current maximum.

### Datadog Logs

Choose **Site** from `us1`, `us3`, `us5`, `eu1`, `ap1`, `ap2`, or `gov`. Supply a logs-write **API key**, not an Application key. **Service** defaults to `sim`; optional **Tags** are comma-separated.

Sim posts to v2 logs intake, exposes top-level row fields as log attributes, and adds `sim_drain_id:`, `sim_run_id:`, and `sim_source:` tags. It sets the reserved `ddsource`, `service`, `ddtags`, and `message` fields, overriding source fields with those names.

Expanded entries are split before compression. Requests are limited to **5,000,000 uncompressed bytes**, **1,000 entries**, and **1,000,000 bytes per entry**, with a defensive 6 MiB wire-size cap. Payloads larger than 1,024 bytes use gzip.

### HTTPS webhook

Supply **URL**, **Signing secret**, optional **Bearer token**, and optional **Signature header name** (default `X-Sim-Signature`). On Sim Cloud, the URL must use HTTPS and resolve to public addresses. Self-hosted deployments apply their [outbound-network policy](/platform/self-hosting/security#the-ssrf-boundary): approved private endpoints and loopback are available, with HTTP only where that policy permits it. Sim blocks cloud-metadata addresses and pins the resolved address for the run to prevent DNS rebinding.

Each chunk includes:

```http
Content-Type: application/x-ndjson
User-Agent: Sim-DataDrain/1.0
X-Sim-Timestamp: <unix-seconds>
X-Sim-Signature-Version: v1
X-Sim-Signature: t=<unix-seconds>,v1=<hex-hmac-sha256>
X-Sim-Drain-Id: <drain-id>
X-Sim-Run-Id: <run-id>
X-Sim-Source: <source-wire-value>
X-Sim-Sequence: <zero-based-chunk-index>
X-Sim-Row-Count: <row-count>
Idempotency-Key: <runId>-<sequence>
```

Sim signs the exact string `${timestamp}.${body}` with HMAC-SHA256 and the signing secret. Recompute using the original request body and reject old timestamps—for example, those older than five minutes—to limit replay. A bearer token, when configured, is sent as `Authorization: Bearer <token>`.

Delivery retries up to three times after the initial attempt: 500 ms, 1 s, and 2 s with ±20% jitter. `Retry-After` is respected on `429` and `503`; non-retryable `4xx` responses fail immediately.

## Checkpoints, bounds, and failures

An opaque cursor advances only after acknowledged delivery. Later failures resume after the last acknowledged chunk, but a crash between remote acceptance and checkpointing can replay data. A database claim prevents overlapping runs for one drain and fences stale workers.

| Bound | Limit |
| --- | --- |
| Database page | 100 rows |
| Source record, transcript, or execution archive before materialization | 1 MiB |
| NDJSON chunk | 4 MiB |
| One run | 100 chunks, 10,000 rows, or 100 MiB |
| Work window / hard deadline | 20 minutes / 25 minutes |

A queued run that reaches its work window schedules continuation. Oversized records and missing execution archives fail visibly without advancing past the incomplete record.

The webhook idempotency key covers retries of one chunk within one run. A later replay has a new run ID; partially accepted destination requests can also repeat rows. Keep source-ID deduplication even when the destination offers its own deduplication.

## Pair with data retention

<Callout type="warn">
Retention does not wait for a drain. Failed delivery or backlog can let cleanup delete records before export. Set a cadence shorter than the retention window and monitor recent runs, progress, and destination receipt.
</Callout>

| Source | Retention category |
| --- | --- |
| Workflow logs and Job logs | Log retention |
| Chats and Chat runs | Task cleanup |
| Audit logs | No age-based audit-retention setting currently |

For a 30-day log window, **Every hour** or **Every day** provides opportunities to export before expiry; cadence alone does not guarantee every row arrives. Source deletion, workspace scope changes, late commits, and persistent failures can still leave gaps.

Your destination owns exported data lifecycle and erasure after delivery. Sim does not remove external objects when source data or a drain is deleted.

## Rotate credentials or delete a drain

Destination credentials are encrypted at rest using key-rotation-aware encryption and are not returned by API reads. An API update can supply a complete replacement credential payload; omitting credentials preserves the stored secret. Source and destination type cannot be changed on an existing drain.

The current settings detail page edits **Enabled** only. Changing credentials there requires recreating the drain, which starts retained-history backfill again and can duplicate archived data. Use a supported API credential replacement when cursor continuity matters; do not delete the existing drain merely to rotate a key.

**Delete** removes configuration and run history, without deleting exported bytes. Create, update, delete, manual-run, and connection-test actions emit best-effort [audit events](/platform/enterprise/audit-logs).

## Self-hosted setup

Enable the feature through enterprise configuration or explicitly set:

```bash
DATA_DRAINS_ENABLED=true
NEXT_PUBLIC_DATA_DRAINS_ENABLED=true
```

An explicit feature value takes precedence over `ENTERPRISE_ENABLED`. When disabled, the page is hidden, mutating drain requests return `404`, and the dispatcher does no work. Billing-enabled deployments retain the Enterprise gate. Keep server and public feature configuration aligned; `bunx sim-setup doctor` checks the pair. See [self-hosted enterprise setup](/platform/enterprise/self-hosted).

The dispatcher requires scheduled calls to `GET /api/cron/run-data-drains`. Set the same `CRON_SECRET` on the app and its caller; the endpoint returns `401` when it is unset. Generate a secret if needed, then install it in both configurations:

```bash
openssl rand -hex 32
```

Helm's `cronjobs.jobs.runDataDrains` and Docker Compose's `cron` service call it hourly when their schedulers are enabled. If neither runs, configure an external scheduler:

```bash
curl --fail-with-body \
  -H "Authorization: Bearer $CRON_SECRET" \
  https://sim.example.com/api/cron/run-data-drains
```

Trigger.dev is optional. The database backend executes the registered runner with at most two active drain jobs per app process; Trigger.dev uses serialized per-drain jobs. Database claims apply in both modes. Verify scheduler calls and actual destination receipt after enabling the feature.
