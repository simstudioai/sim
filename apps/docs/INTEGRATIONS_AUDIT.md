The original pass reviewed 306 integration pages: 281 generated references and 25 authored pages (the integration overview, A2A, and registered connection guides). The baseline is staging commit `2676575f218c2080c0cf1e437be9100d320b0134`. [EDITORIAL_GUIDE.md](EDITORIAL_GUIDE.md) defines the ongoing format; [scripts/README.md](../../scripts/README.md) explains regeneration and ownership.

The current staging sync contains 308 integration pages. The added Help Scout reference received the same disclosure treatment and a copy pass that removed repeated capability lists while retaining connection, trigger, and knowledge-base setup. Authentication and webhook signatures were checked against the owning implementation and [Help Scout authentication](https://developer.helpscout.com/mailbox-api/overview/authentication/) and [webhook documentation](https://developer.helpscout.com/webhooks/). ## Assessment and changes

The action, input, output, and trigger tables are a useful lookup structure. The problems were repeated capability lists, setup instructions buried below long references, inconsistent headings, and unsupported guarantees about permissions, expiry, billing, and destructive operations.

- Keep connection requirements before use guidance and actions. Put triggers after actions, followed by shared schemas and operational notes. Preserve existing heading anchors while standardizing sentence case.
- Keep all action names, input fields, conditional requirements, output paths, scope lists, callbacks, and working examples. Replace filler descriptions with an empty description when the source supplies no information; an undocumented output is not proof that the action returns nothing.
- Edit descriptions at their block, tool, trigger, or OAuth owner. Preserve authored `MANUAL-CONTENT` regions during regeneration. Edit registered connection guides directly.
- Group Sportmonks by the existing operation-selector families without changing its 221-action order, names, fields, or existing action anchors.
- Fold useful FAQ answers into setup, limits, or troubleshooting. Remove repetitive explanation and redundant components. Remove assets only after checking all consumers.

## Method and verification limits

Three parallel lanes covered every page. Each lane read the complete original authored content, reviewed generated action and field prose, and retained the association between repeated descriptions and every operation/field where they appear. Repeated schema prose was deduplicated for review. Canonical implementation and primary provider documentation support consequential claims; the ledger below records page-level changes and sources.

A second set of reviewers compares the rewritten copy against the originals for useful-information loss and unsupported replacement claims. Generated output is compared independently for action order, table fields/types/requiredness, authored-region preservation, anchors, and deterministic regeneration. Production rendering, internal links, Markdown delivery, and repository/CI checks are separate checks.

This is exhaustive page and static-copy coverage, with targeted primary-source verification of consequential setup, permissions, lifecycle, billing, and destructive behavior. It does not certify every provider field against a live API, prove subscription entitlement, or exercise authenticated external mutations. An identity/token probe does not prove resource access, every scope, or future token validity.
